# 🛫 着手前プリフライトチェックリスト（必読・常時適用）

非自明なタスク（実装・修正・デプロイ）に着手する前に、必ず以下を **思考の冒頭で順番に確認** する。スキップ禁止。違反した場合はユーザーから「§番号 違反」と指摘されうる。

## 0️⃣ 時刻認識（§34-1）
思考冒頭で `date '+%Y-%m-%d %H:%M (%a)'` を確認。21時以降は休息提案を併記。

## 1️⃣ ルール索引参照（§0 / persist-policies）
ワークスペース直下の **`RULES-INDEX.md` の「即答カード」と「随時メモ」** を該当範囲だけ読む。長セッションでは途中でも戻る。

## 2️⃣ §33-A 事前調査（最低3ステップ・新領域/失敗領域/iframe・sandbox・CSP・セキュリティで必須）
- ① 公式ドキュメント（`fetch` / `tavily` / `WebFetch`）
- ② 既知事例（`github` MCP code search）
- ③ 失敗事例 / workaround（`tavily` / `google-search` で「issue / limitation / does not work」）
- ④ 社内ナレッジ（`rag` MCP / `troubleshooting.md`）

着手前に **「調査の要点 1-3 行」をユーザーへ要約報告**する。

## 3️⃣ §14 同一失敗の繰り返しチェック
直近で「治らない / 改善されない / 同じ問題」と指摘されていないか確認。該当する場合は **同じアプローチ禁止**。代替案を最低 2 つ（メリット/デメリット/リスク付き）提示してから着手。

## 4️⃣ §15 完成度基準を念頭に置く
着手時から「ルール遵守 / 日本語コメント / エラーハンドリング / 検証可能性」の 4 点が満たせる設計か確認。「とりあえず動く」で止めない。

## 5️⃣ 行動の一言宣言（任意だが推奨）
着手直前に 1 行で宣言する：
> 「§33-A 調査済み（要点: …）／ §14 同一失敗なし／ §15 完成度を満たす設計で着手します」

## 6️⃣ §41 ユーザーへ確認・依頼する直前（一問一答）
送信直前に **問いが 1 つだけか**、複数あるなら **最優先 1 問に分割したか** を確認する。次の確認へ進むときは **「次に〇〇を確認してもよいですか？」と許可を得てから**（§41）。

## 違反した時の振る舞い
- ユーザーから「§番号 違反」と指摘されたら、**即座に手を止めて方針再検討**
- 言い訳せず、何を見落としたか 1 行で認め、代替案へ転換
