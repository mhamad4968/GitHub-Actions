# kintone 開発（JavaScript / カスタマイズ）

## イベント・ JavaScript API

- **イベント登録は原則 `kintone.events.on` を使う。** 別手段が適切な場合は、**例外理由を日本語コメントで1行以上**書く。
- **フィールドコードは推測しない。** 必ず `kintone-ai-lab/kintone-apps.md` の一覧または `npm run app:fields <アプリID>` の出力と一致しているコードだけを使う。存在しないフィールドへのアクセスは書かない。

## 生成した JS の保存場所（この環境）

- **ワンオフ・検証用・生成ドラフト**: `kintone-ai-lab/scripts/` に保存してからデプロイ手順へ回す（ユーザ指定の「プロジェクト内の scripts」はここを指す）。
- **画面カスタマイズ本番ソース**: `kintone-ai-lab/customize/<アプリIDまたはフォルダ名>/desktop.js` に反映する。
- **アップロード前の退避・共有用**: `Documents/kintone-src`（WSL: `/mnt/c/Users/mhamada202408224/Documents/kintone-src`）も使ってよい。

## デプロイ・JBIS ダッシュ UI・表レイアウト（運用）

- **デプロイ指示は1セットで明示する**: 誤アプリ防止のため、**アプリID**・**実行コマンド**（例: `npm run deploy:654`）・**アップロード対象のソースパス**を同じ返答内に書く。エージェントがデプロイする場合も、実行前にその3点を揃えて確認する。
- **UI 文言バンプの記録**: ダッシュ等で `JBIS_DASH_UI_COPY_VERSION` や同等の「キャッシュ・版切り」用定数を変えたら、**コミットメッセージに1行**、または **`RULES-INDEX.md` の随時メモ**に **日付＋変更の要約**を残す（後から「どの版か」を追えるようにする）。
- **表の列数・固定列を変えるときのチェックリスト**: **thead と tbody の列順・セル数**が一致しているか、**`colSpan`**、**sticky の `left` / `width` / `z-index`**、**表の `minWidth`**、**ツールチップ・ブロック直下の説明文**まで一緒に直したかを確認する（片方だけ更新しない）。
- **セッション区切り（ユーザー側メモ）**: 大きな機能が一区切りついたら、ユーザーが **完了した単位を1行**（例: 「工種別表から会社列を削除」）残すと、次回の文脈復帰が安定しやすい。

## REST API / 更新回数

- **API 制限（ゲスト除く 1 時間あたりのリクエスト上限）を意識する。**
- 多数レコードを更新するときは **可能な限り一括更新 API（例: `records.json` の PUT で複数件）や既存の一括系に寄せる。** 1 件ずつのループ更新をデフォルトにしない。分割が必要なときは **バッチサイズと待機**をコードまたはコメントで明示する。

## kintone 一覧 `query` の事前検証（手戻り防止）

- **一覧URLの `query=` は実装前に必ず「最小クエリ」で検証する。** 例: `$id in (1)` / `field = ""` / `field in ("値")` など 1〜2 本で文法・フィールド型の可否を先に確定する。
- **サブテーブル・関連レコード・ドロップダウン等は、演算子制約が強い前提で調べてから書く。** 不確実ならまず「そのフィールド型で使える演算子」を確認する（公式ヘルプ/実機の最小クエリ）。
- **否定条件は `not (...)` を前提にしない。** 必要なら `not in` など、一覧クエリで通る形を優先する（実機検証で確定）。
- **ダメだった時の即時代替**: クエリが通らない/`like` が不安定なら、API で候補 `$id` を収集して **`$id in (...)`** に寄せる（必要なら上限・分割・キャッシュを設計）。

## Claude Code（ターミナル）/ MCP の使い分け（手戻り防止）

- **ターミナルでの自動修正（Claude Code）**を使う場合でも、**フィールドコードは推測しない**。`kintone-ai-lab/kintone-apps.md` または `npm run app:fields <ID>` を正本にする。
- **仕様・制限・API パラメータが論点**なら、MCP（kintone / fetch / google-search）で公式へ回帰してから実装する（推測で突っ込まない）。
- 導入メモ（人間向け）: `kintone-ai-lab/docs/claude-code-terminal-setup.md`

## kintone開発の鉄則（厳守）

- **非同期処理の制御**: API を叩く処理は **`async/await` を基本**にし、`kintone.events.on` の handler は **event を正しく return** する（`Promise` チェーンで握りつぶさない）。
- **フィールドコードの整合性**: 実装前に「使用するフィールドコード一覧」を **`kintone-ai-lab/kintone-apps.md` / `app:fields`** で確認する。**不明なフィールドコードが出たらユーザーに質問**し、推測で進めない。
- **エラー可視化**: エラーは console だけに出さず、必要に応じて **画面上の表示（バナー/注意文/非表示解除など）**で利用者が状況を把握できるよう配慮する（例: `kintone.app.record.setFieldShown`、ヘッダ/本文先頭のメッセージ）。
- **一括処理の最適化**: レコード更新は 1件ずつのループをデフォルトにせず、可能なら **複数件更新・bulkRequest 等**の一括方式を検討する（レート制限・失敗時リトライも考える）。
- **ルックアップ/計算の反映**: ルックアップや計算フィールドは **API 更新だけでは即時反映されない**ことがある。必要なら **再計算（recalc）**・運用手順・別の保存導線など、反映ロジックを設計してから実装する。
- **同時リクエスト制限**: 1アプリに対する **同時接続数/同時実行**を前提に、ループ内での API 並列実行は原則しない（`Promise.all` 多用禁止）。**bulkRequest / 一括更新**を優先し、やむを得ず分割するときは **バッチサイズ**と **待機**を入れる。
- **field-spec-export の常時参照**: 実装開始前に必ず `kintone-ai-lab/docs/field-spec-export.md` を読み、対象アプリの最新フィールド構成を把握する。古い/不足と判断したら、ユーザーに **再エクスポート（または `app:fields` 実行）**を促す。

## AIによる自己レビュー（コード提示後に必ず実施）

- コード提示後、次の3点を自分でレビューして **簡潔に結果を報告**する。
  - **kintone制限事項**: API 制限・同時実行・非同期 `return` 漏れ・ルックアップ/計算の反映などの制約を踏んでいるか
  - **保守性**: フィールドコードが推測でなく正本に基づくか／定数管理されているか
  - **ユーザー体験**: 処理中表示（必要なら）とエラー通知（画面上の可視化含む）が考慮されているか

## 「AIへの丸投げ」を加速させる魔法のフレーズ（人間向け）

ユーザーが新機能を依頼するときは、技術指示を省いて次の形でよい。

> 「[アプリ名/ID] に、[やりたいこと] という機能を追加して。現在のルールと設計図に従って、設計・実装・自己レビューまで一気に進めてください。」

この依頼を受けたら、エージェントは自律的に次を行う（抜けを作らない）。

- `kintone-ai-lab/docs/field-spec-export.md` を読み、対象フィールドの有無を確認
- 無ければ「フィールドを作ってください」を逆提案（推測で進めない）
- あれば本 `.mdc`（手戻り防止）に従って設計・実装
- 完了時に「動作確認チェックリスト（3項目）」＋「自己レビュー（3点）」を出して報告

## 自律開発サイクル（今後のイメージ）

- **丸投げの開始**: 「魔法のフレーズ」でやりたいことを伝える。  
  例: 「〇〇アプリに、二重登録防止のチェック機能をつけて。ルール通りに進めて」
- **AIの自律思考**: `field-spec-export.md` を読み、`kintone-javascript.mdc` の鉄則・保守性ルールに従い、設計→実装→自己レビューまで進める（不足があれば再エクスポート/追加情報を逆提案）。
- **あなたの最終確認**: AIが提示する **「動作確認チェックリスト（3項目程度）」** に沿って、kintone 画面で確認する。
- **完了**: 動けばOK。違和感があれば「ここが使いにくい」と一言伝えるだけで、AIがルールに基づき修正し、必要なら **「ルールの改善案」**を 1 つ提案する。

## 画面キャプチャ（スクショ）から要件定義する（画像解析プロトコル）

ユーザーから kintone の設定画面・エラー画面・レコード画面などの**スクリーンショット**が提供された場合、エージェントは次を自律的に行う。

- 画像から読み取れる範囲で **フィールドのラベル/配置/入力タイプ/現在値/エラー文言**を整理する（OCR/画像理解）。
- `kintone-ai-lab/docs/field-spec-export.md`（設計図）および `kintone-ai-lab/kintone-apps.md` と突合し、**差分（ラベルはあるがコード不明、型が違う、フォーム未配置など）**を列挙する。
- 差分が原因で実装にリスクがある場合は、推測で進めず **「再エクスポート（または `app:fields`）を促す」**か、必要最小の追加情報をユーザーに依頼する。

## ルール自己改善（Self-Optimization）

- 開発完了後、もし `.cursor/rules/` 内のルールに改善の余地（より効率的な書き方・新しく発見した kintone の仕様・抜け漏れ防止の手順など）を見つけた場合は、最後に **「ルールの改善案」**を **1つ**提案する（実際の追記はユーザーが「追記して」と言ったときだけ行う）。

## ツール・環境の自律保守（セルフ・アップデート）

**人間のコントロール下**で「古いまま放置」と「更新して壊す」を避ける。バージョン変更は **必ず承認後**（勝手に本番相当の環境を壊さない）。

### アップデートの検知と提案

- **セッション開始時**、または **`package.json` / ロックファイル / MCP 設定を触る直前**に、必要なら更新の有無を確認する。
- 主な対象:
  - **Claude Code**: 公式ドキュメントに従い CLI のバージョン・インストール手順を確認（`claude --version` / `claude doctor` 等）
  - **`@kintone/rest-api-client`**（`kintone-ai-lab` の devDependencies 等）
  - **MCP サーバー**（`~/.cursor/mcp.json` で参照している `npx`/`uvx` パッケージと固定版の有無）
- アップデートがある場合は **変更内容・Breaking の可能性・影響範囲**を短く整理し、**実行の承認**をユーザーに求める（未承認ならバージョンを上げない）。

### アップデート実行プロトコル（承認後）

1. **バックアップ**: **Git コミットはユーザーが明示して承認したときのみ**。それ以外は `package.json` / `package-lock.json` の差分を説明し、必要ならユーザーに手元で退避（コピー・stash）を依頼する。
2. **依存の更新**: `kintone-ai-lab` 直下で `npm outdated` を参考にし、**ピンポイントに**上げる（無関係な全面メジャー上げはしない）。
3. **クリーンインストール**: 競合が疑われるときは、承認を得たうえで `rm -rf node_modules && npm ci`（またはプロジェクト既定手順）を検討する。
4. **設定ファイル**: `~/.cursor/mcp.json` 等は**秘密をログに出さず**、変更はユーザー承認＋最小差分。

### 正常性確認（検証サイクル）の義務化

アップデート実行後、環境で使える範囲で次を試し、**通否を報告**する。

- **型/Lint**: `npm run typecheck:utils` / `npm run lint:customize`（`kintone-ai-lab` にあるとき）
- **接続**: `npm run kintone:test`（`.env` が整っているとき）
- **サブプロジェクト**: 触れたなら該当ディレクトリの `npm run build` 等

異常時は **ロールバック方針**（`package.json` / ロックを戻す、該当パッケージの直前バージョンへ戻す）を提案し、原因を短く整理して報告する。

## 修復・リファクタ後の検証義務（2026-04-13 追加: 654 ダッシュボード教訓）

### イベントバインド確認

- モジュール分割・`render` 関数改修後は、**再描画のたびにイベントリスナーが再バインドされるか**を必ず検証する。
- 確認対象: `mouseover`/`mouseout`（ホバー）、`click`（リンク遷移）、`change` 等すべて。
- **サイレント障害**（エラーは出ないが動かない）は console.log を一時挿入して発火有無を確認する。

### 全パターン網羅テスト

- ダッシュボード系は**全テーブル/全タブ**で動作確認する（1つで動いても他で壊れている前例あり）。
- ツールチップ等の浮動要素は `z-index` / `overflow` / `position` を確認（表に隠れる問題）。

### 「修復完了」報告時のルール

- **「直した」とだけ言わない**。報告時に**具体的な検証手順**を添える:
  - 例: 「全体タブ → 4月の実績セルをホバー → コメント表示を確認」「固定費 → 実績数字をクリック → レコードが開くことを確認」
- ユーザーが実機で確認するまでは**未完了**として扱う。
