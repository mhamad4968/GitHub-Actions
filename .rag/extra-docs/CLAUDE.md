# Claude Code / エージェント向け（本リポジトリ）

作業開始時に読む。**フィールドコードは推測しない。** **的確さ**のため、**判断が分かれるところは公式・正本で確認**し、**レコード内容を変える作業は実測データのビフォー・アフター**で示す（各節のルール）。迷ったら下記の優先順位で「正」を取りにいく。

### 自律サイクル（全体像）

**計画**（Plan of Action・制約先出し・参照した公式）→ **調査**（公式回帰・**環境 Health Check**・`app:fields` / 型）→ **実装**（正本・推測禁止）→ **検証**（コマンド・**レコード JSON ビフォー／アフター**）→ **報告**（黄金 3 ステップ＋`<details>`）。開発環境のズレは **着手前と区切り**で潰し、実装直後の手戻りを減らす。

**正本ズレの修正・健康診断を依頼されたとき、および下記「セッション開始時」で実装作業に入るときは、次の 4 ステップをこの順で踏む**（レコードを触らない作業では **3 の JSON は「該当なし（スキーマのみ）」**、**実行ログ・コマンド要約は必須**）:

1. **Health Check**（実アプリと **`kintone-apps.md` / 型**の突合・一覧は下記 **「プロジェクト全体の健康診断」**）  
2. **Plan of Action**（何をどう直すか・対象 appId・履歴追記方針）  
3. **エビデンス**（**実行ログ**（`app:fields` / `app:types` の要点・終了コード）＋レコード操作があるとき **JSON ビフォー／アフター**）  
4. **黄金 3 ステップ報告**＋`<details>`（Health Check 結果・diff 要点・エビデンスを details に）

## 依頼の解釈・自己判断・ナレッジの貯め方（迷わせない）

**依頼が短い・あいまいでもよい**: 会話の文脈・本リポの正本から**合理的に補完して進めてよい**。ただし **誤ったアプリにデプロイする**・**本番トークンをログに出す**・**フィールドコードを推測して書き換える**など **取り返しが重い**ところだけは、実行前にユーザーまたは正本で確認する。

**ユーザーは技術判断をエージェントに委ねることが多い前提**: 細かい実装方針・手順の選択は**エージェントが正本に沿って決めて進める**。応答には**何をどうしたか**と**なぜそうしたか（短く）**を書く。永続化すべき決定は **`RULES-INDEX.md` 1 行**や正本へ残す。**ユーザーに聞くのは**業務の優先（何を先にしたいか）・非技術の可否・および上記の**取り返しが重い**操作だけに絞る。

**仕様の深読み・忖度禁止（境界線）**: **依頼や正本に書かれていない**部分で、**A 案（安全だが手間）**と **B 案（便利だがリスクあり）**のような**トレードオフ**がはっきりするときは、**勝手に片方を選ばない**。**Plan of Action**（または宣言に準ずる短い箇条書き）で**両案を提示**し、**メリット／デメリットを短く**書いたうえで**ユーザーの選択を仰ぐ**。「的確さ」の名の下に**仕様を捏造**しない。

**判断材料をこの順で見る**（次のエージェントが同じ迷いをしないように、ここに載っている前提で動く）:

1. 本ファイル **`CLAUDE.md`**（儀式・優先順位・禁止事項）  
2. **`kintone-apps.md`**（**「アプリ間依存関係マップ」**・該当アプリの見出し・**履歴テーブル末尾＝新しい方**）  
3. **`types/kintone-<appId>.d.ts`**（生成型）  
4. 領域ごとの README / **`docs/*.md`**（例: `security-next-automation/README.md`、**`docs/claude-github-index.md`**）  
5. **`RULES-INDEX.md`** の随時メモ（日付行で「どの話題の正本がどこか」）  
6. **`.cursor/rules/*.mdc`**  
7. **`chat-sessions/checkpoint-latest.md`**（**作業の途中経過・未完了だけ**。記述が正本と食い違うときは**正本を採用**し、チェックポイントを直すか **`(要確認)`** と残す。詳細は **`docs/agent-restore-checkpoint.md`**）

**自己判断したら必ずストックする**（チャットの暗記に頼らない）:

| 残す内容 | 置き場所 |
|----------|----------|
| 事実（決まった仕様・フィールド・コマンド・URL） | 既存の**正本**（`kintone-apps.md` 追記、該当 `docs/`、`.mdc`） |
| 「こう決めた」「例外はこのときだけ」 | 正本に短く追記し、**`RULES-INDEX.md` に日付＋1 行** |
| その日の経緯・試行 | **`chat-sessions/YYYY-MM-DD.md`** または `C:\Claudeとの会話メモ\` の当日ファイル |
| チャットが消えても戻したい「いまの現在地」 | **`chat-sessions/checkpoint-latest.md`**（運用・優先順位は **`docs/agent-restore-checkpoint.md`**。**正本より下位**） |

**推測と事実の区別**: 正本に無いコード名・フィールド名は**事実として書かない**。仮説で進めた場合は PR / 会話メモに「未確認で仮置き」と明記し、確認後に正本へ昇格する。

## 作業開始前の宣言（Plan of Action・思考の言語化）

**狙い**: 「良かれと思った修正」がユーザーの意図とズレるのを防ぐ。**期待値の不一致**を早い段階で潰す。あわせて **「後出しジャンケン」**（実装後に「kintone の仕様では無理でした」と判明する）を防ぎ、**技術的限界・トレードオフを先出し**してユーザーが**着手前に軌道修正**できるようにする（**守護神ルール**）。

**次を満たすときは、コードを書く前に必ずチャットで宣言する**（箇条書きでよい）:

- **複数ファイル**にまたがる修正、または **1 アプリだが挙動・データに広い影響**（保存イベント・API 同期・ルックアップ等）  
- **共通部品**（`utils/`・`kintone-common.ts`・複数 `customize/*/desktop.js` に触れる変更）

**宣言に含めること**（**1〜3 に加え 4 は必須**。**5 は条件付き必須**—下記参照。該当が無いときは **「制約・懸念なし（この範囲では標準的に実現可能）」** と一行でよい）:

1. **目的**（何のためか一文）  
2. **触るファイル／アプリ ID**（列挙）  
3. **想定される影響**（他アプリ・他スクリプト・既知の依存は **`kintone-apps.md` の「アプリ間依存関係マップ」**を見て書く）  
4. **できないこと・懸念点・制約（先出し）** … **着手後に「実は無理」と言わない**ため、**今回の依頼について**次を**先に**挙げる（分からなければ **「要確認」** と書き、公式または正本で当たる）。  
   - **kintone 標準機能の限界**（アプリ設定・プラグイン無しで不可能に近いこと、モバイル／ゲスト空間の制約、レコード一覧・印刷・権限の壁 等）  
   - **API・同時実行・レート・Bulk** など、**大量件数・短時間ループ**が絡むときの**見込みリスク**  
   - **トレードオフ**（A を満たすと B が犠牲、別アプリ・外部システムが必要 等）  
   - **正本に無い前提**で進む場合の**仮置き**と**確認が必要な点**  
5. **参照した公式（条件付き必須）** … **kintone の制限・API 仕様・新 API・レート制限**など、**記憶や推測だけでは確信が持てず**公式を当たったときは、**取得したページの URL** を**宣言に列挙**する（**`着手前の情報収集` の「公式への回帰」**に従い、MCP **fetch**・WebFetch・**`curl`**・**一時的な Python** 等で **cybozu.dev** 等を取得してよい）。**迷いがなく定型どおり**なら **「公式参照不要」** と一行でよい。

**その後の進め方**:

- **ユーザーが止める・別案を出す**余地を残すため、宣言のあと **「この方針で進めてよいか、または止めたい点があれば一言ください」** と書く。  
- **返答待ちが難しい非同期**では、宣言直後に **「異論がなければこの宣言どおり着手します」** と明記し、**単純な 1 ファイル・文言のみの修正**にはこの節を**省略してよい**。

### 自律の限界（ギブアップ・分割・ペアプロ）

**次のときは、一気に自律完了を狙わず、方針を切り替える提案をする**（無理な大規模変更でリポや本番を壊さない）。

- **同じ変更が 5 つ以上の別 appId** に**同時に**波及しそうなとき（**分割提案**: バッチ 1 は app A〜C、バッチ 2 は … など**段階に分ける**）。  
- **Health Check** や依存マップを見ても**確信が持てず**、誤った一括更新のリスクが高いとき。  

**提案の例**: **「分割して先に N アプリだけ進めてよいか」**、**「ペアプログラミング（一歩ずつ確認）モードに切り替えたい」**。**コンテキストの限界**を理由に**正直に書いてよい**。

## 着手前の情報収集（最新化・MCP）

ユーザーは**取りかかる前に**、可能な範囲で**最新情報を取り入れる**ことを期待している。**本格的に着手する前**（新 API・セキュリティ・外部サービス手順・バージョン依存・Breaking change が絡むとき）は、リポジトリ内の静止ファイルだけに頼らず、次を**状況に応じて**使う。

| 手段 | 使いどころ（例） |
|------|------------------|
| **MCP**（セッションで有効なもの） | **fetch** … 公式ドキュメントの該当ページ。**google-search** … 仕様名・エラーで調査。**cve-search** … CVE 番号・影響確認。kintone / GitHub 等、接続されているサーバがあれば優先。 |
| **WebSearch / WebFetch** | MCP が無い・足りないときの補完。リリースノート・Deprecation。 |
| **公式の起点** | kintone は **`docs/cursor-official-references.md`「0. kintone」**の URL を正とし、**公式 > 非公式ブログ**で解釈する。 |

### Claude Code（ターミナル導入）

導入・運用メモ: **`docs/claude-code-terminal-setup.md`**（公式 URL・インストール・運用テンプレ）。

**環境の整合性（フィールド・正本）**: 作業対象アプリの**フォーム**（フィールドコード等）が **`kintone-apps.md`**（該当見出し・**履歴末尾**）と**食い違っていないか**、**着手時**に **`npm run app:fields -- <appId> [--markdown]`** と必要なら **`npm run app:types -- <appId>`** で**自律的に突き合わせる**。差分・削除・リネームがあれば **正本更新**または **Plan of Action／完了報告の `<details>`** に**先に書く**（「実装してから気づく」手戻りを防ぐ）。詳細な一覧手順は **`環境整合性のチェック（Health Check）`**。

### 公式ドキュメントへの回帰（Source of Truth・ハルシネーション防止）

**狙い**: **古い記憶**や**推測だけ**でコードを書き、後から仕様と食い違うのを防ぐ（**的確さ向上**）。

**次のときは、着手前に必ず公式を取得して内容を確認する**（手段は **MCP fetch**・**WebFetch**・**`curl`**・**一時的な Python** など、**その環境で動くもの**でよい）。**優先ドメイン**は **cybozu.dev**（kintone 開発者向け）。入口は **`docs/cursor-official-references.md`「0. kintone」**。

- **制限事項・上限・非対応**が論点になるとき  
- **新しい API・パラメータ・廃止予定**が論点になるとき  
- **REST の挙動・レート・Bulk**で判断が分かれるとき  
- リポジトリの正本と**頭の中の仕様が一致しない**とき  

**取得したら**: 応答に**根拠となった公式 URL**を**短く列挙**する。**Plan of Action を出すタスク**では、上記を踏んだ場合 **宣言の「5. 参照した公式」**に**同じ URL**を書く（重複でよい）。Plan of Action を**省略する**小さな作業でも、**判断が分岐したら**チャットに**URL を添える**義務は同じ。

**毎回必須にしない**: 明らかにローカル完結の 1 行修正・**既に正本と公式で確定**している作業では、上記「回帰」を省略してよい。使った外部情報は応答に**参照 URL を短く**示すとよい（再検証しやすい）。

## 環境整合性のチェック（Health Check・自律パトロール）

**狙い**: **開発環境そのものを腐らせない**（`.env` 欠落・古い依存・**kintone-apps.md と実アプリのズレ**）ため、エージェントが**定期的・マイルストーン時**に**一通り確認**し、異常を**先に報告**する。

**次のタイミングで実施する**（**自律的に**。ユーザーが言わなくてもよい）:

- **これまでと別の appId** に**初めて**本格的に着手するとき  
- **大きな作業の区切り**（大きな PR 直前・複数アプリ横断の変更の完了時・長時間セッションのまとめ 等）  
- ユーザーから **「環境を確認して」「Health Check」** 等の依頼があったとき  

**確認の骨子**（**環境で使えるものだけ**でよい。失敗したらログを報告に残す）:

| 観点 | 行うこと |
|------|----------|
| **`.env`・認証** | **`npm run app:types -- <対象appId>`** または **`npm run app:fields -- <対象appId>`** を試し、**フェイルファスト**で示される**不足変数・権限**が無いか。 |
| **型・フィールド正本** | 上記が通れば **`types/kintone-<appId>.d.ts`** の有無・更新要否。出力を **`kintone-apps.md` の履歴・見出し**と**目視で矛盾がないか**（フィールド削除・コード変更の取りこぼし）。 |
| **npm・依存** | **`npm audit`**（要約）・**`package.json` と `docs/dependency-upgrade-backlog.md`** に**既知の先送り**がないか**軽く照合**（**無関係な全面更新はしない**）。 |
| **GitHub（任意）** | **`gh` が使えるとき** … **`gh api`** / **`gh workflow list`** 等で、**セッションが触る Actions・ブランチ保護**の異常が無いか**軽く**。使えなければ**省略でよい**。 |

**報告**: **異常・ズレ・要ユーザー対応**（`.env` 不足、正本の更新必須、audit の高リスク 等）は、**Plan of Action**、または**完了報告**の **`<details>技術的な詳細`** に **「Health Check: …」** として**箇条書きで必ず含める**。**問題なし**のときは **「Health Check: 異常なし（対象 appId: …）」** と一行でよい。

### プロジェクト全体の健康診断（`kintone-apps.md` と実環境の一括突合）

**トリガ**:

- **新セッションで、kintone 実装・スクリプト・customize などコードに手を入れる前**（**ユーザーが毎回言わなくてよい既定運用**）。**4 ステップ標準フロー**で**全対象 app**のフィールドと **`kintone-apps.md`** を突合し、ズレがあれば**一括で履歴追記・型同期**し、**実行ログ**と（レコードを触らなければ **実データは該当なし** と明示したうえで）**黄金 3 ステップ**で報告する。  
- ユーザーが **「プロジェクト全体の Health Check」「全アプリと正本を揃えて」「健康診断」** などと**明示**したとき、または **定期的パトロール**として実施するとき。

**手順の骨子**:

1. **対象 appId 一覧**を決める（**`kintone-apps.md` の見出し**・**`customize/` 配下の数値ディレクトリ**・ユーザー指定を突き合わせ。**権限・トークンで取れない ID** は一覧に「未取得」と明記）。  
2. 取れる各 ID について **`npm run app:fields -- <id> [--markdown]`**（必要なら **`npm run app:types -- <id>`**）で**実フォーム**を取得し、**`kintone-apps.md` の該当見出し・履歴末尾**と比較。  
3. **ズレがある app** については **`kintone-apps.md` は追記のみ**—**新しいスナップショットを履歴表として末尾に追記**し、必要なら見出し直下の説明を**追記で**更新（既存行の削除はしない）。**`types/kintone-<id>.d.ts`** を **`app:types`** で再生成。  
4. 上記を **`自律サイクル` の 4 ステップ**（**Plan of Action** → 実装・正本更新 → **エビデンス**※レコード変更時のみ JSON → **黄金 3＋details**）で**まとめて報告**する。  

**5 app 以上や確信が持てない場合**は **`自律の限界`** に従い**分割**を提案する。

## ツール・依存関係・MCP のバージョン（随時アップデート）

ユーザーは**ツールや MCP に新しい安定版・セキュリティ修正**があれば、**判断して更新**してほしいと期待している。**次のタイミング**で、公式リリースノートや npm／GitHub Releases を**軽く当たり**、取り込み判断をする。

| きっかけ | 行うこと |
|----------|----------|
| **`package.json` / ロックファイル**を触る作業の直前・直後 | 対象パッケージの**最新セマンティック**を確認。**パッチ・セキュリティ**は積極的に。**メジャー**は Breaking の有無を読み、`npm test` / `npm run lint` 等で確認してから。 |
| **GitHub Actions** の `actions/*`・`uses:` を編集するとき | **ピン留め**（`@v4` 等）の推奨範囲を公式に合わせる。 |
| **MCP サーバ**（`npx`・`uvx`・拡張のバージョン指定）を扱うとき | 各サーバの README / releases を確認し、**指定バージョンを更新**できるなら更新。**設定ファイル**は多くが **`~/.cursor/mcp.json`**（ユーザー環境）— リポジトリにコミットしていない場合は、変更内容を**応答で短く伝え**、ユーザーが反映しやすいようにする。 |
| **セキュリティ・CVE** が話題になったとき | **cve-search** や公式アドバイザリで影響範囲を確認し、必要なら依存関係を上げる。 |

**無理な全面更新はしない**: 依頼と無関係な**全依存の一括メジャー上げ**は、別タスクとして切り出すかユーザーに一言する。**更新したら** `RULES-INDEX.md` に **日付＋1 行**（何をどの程度上げたか）を残すとよい。

**意図的に先送りした依存・audit 対応**は、チャットの記憶に頼らず **`docs/dependency-upgrade-backlog.md`** を正本とする。`package.json` を触る・四半期見直し・セキュリティ監査のときに開き、解消した項目はそのファイルと **`RULES-INDEX.md`** を更新する。

**[ツール保守ルール]**: **`.cursor/rules/kintone-javascript.mdc`** の **「ツール・環境の自律保守（セルフ・アップデート）」** セクションを参照（承認必須のバージョン変更・検証サイクル・ロールバック方針の正本）。

## 本ファイル（`CLAUDE.md`）のメンテナンス

**`CLAUDE.md` 自体も随時アップデートの対象**（ユーザーが毎回言わなくてよい）。エージェントは次のタイミングで、**追記・改稿**してよい。

| きっかけ | 行うこと |
|----------|----------|
| **ユーザーと新しい約束**（運用・依頼の解釈・ツール方針など） | 該当セクションに**短く反映**。重複する段落は**統合**。 |
| **他の正本と矛盾** | **`kintone-apps.md`・`RULES-INDEX.md`・`docs/*.md`** 等と突き合わせ、**事実に合わせて** `CLAUDE.md` を直す。必要なら他ファイルも同じセッションで整合。 |
| **リポジトリの事実が変わった** | npm スクリプト名・パス・デプロイ手順・推奨コマンドを**現状に合わせる**。 |
| **Claude Code / Cursor / Anthropic の推奨が変わった** | **公式・ドキュメントを Web / MCP で確認**し、本リポに取り込む価値があれば**1〜数行**足すか既存を更新（長文化しすぎない）。 |

**合意したルールを勝手に消さない（削除禁止）**: ユーザーと**定めた運用・儀式・チェックリスト・節見出し**を、エージェントが**依頼なしに削除・丸ごと空白化**しない（**長いから**・**重複っぽいから**だけを理由にした**静默削除**は禁止）。**変更・廃止**するときは **ユーザーに明示確認**するか、**追記で「旧」「移行先」**を残し**要件が読み取れる状態**にする。**重複の統合**はよいが、**義務・トリガ・例外・手順**が**失われない**ようにする（統合後に**箇条書きで復元できる**粒度を維持）。

**末尾に「変更履歴」を必須にしない**（代わりに **`RULES-INDEX.md` に日付＋1 行**で「`CLAUDE.md` を更新（要約）」と残す）。**自己参照で肥大化**しないよう、重複は**統合**してよいが、**上記の削除禁止**に従う。

**他の正本も同様**: **`kintone-apps.md`**（**追記のみ**・履歴削除禁止）、**`RULES-INDEX.md`** の日付行、**`.cursor/rules/*.mdc`** など、**ユーザーが合意した内容**を**勝手に削らない**（**本節と同じ精神**）。

## バックログ・Issue パトロール（放置課題の掘り起こし）

**狙い**: 時間が経って**忘れ去られた Issue** を、**現在のコードベース・正本**と照らし合わせて再分類し、プロジェクトの**腐敗（仕様ドリフト・幽霊タスク）**を防ぐ。**管理人**的な自律動作。

**いつやるか**（いずれか）。

- ユーザーから **「Issue を整理」「バックログパトロール」「放置タスクを見て」** などと依頼があったとき → **そのセッションで実施**。  
- **運用上の目安**: **週に一度程度**、未完了 Issue を軽く見返すのが望ましい（カレンダー連動は環境依存のため**強制はしない**。**トリガは主にユーザーの依頼**とする）。

**手順の骨子**（ツールは環境に合わせる。例: **`gh issue list`** / GitHub の検索。`gh` が無い場合は Web またはユーザーに一覧の貼り付けを依頼）。

1. **未完了 Issue** を列挙（ラベル・古い順でもよい）。  
2. 各件について **現在の `kintone-apps.md`・`types/`・該当 `customize/` / `scripts/`・`docs/`** と突き合わせ、次のラベル付けで**提案**する（**勝手にクローズ・大量編集はしない**。判断はユーザー）。  
   - **今なら短時間で直せそう**（差分が小さい・正本が揃っている）  
   - **仕様・正本が古い**（Issue の前提がもう違う → **更新・クローズ・書き換え**のどれか提案）  
   - **まだ有効だが優先度見直し**（ブロッカーや依存の変化を一言）  
3. 結果は **チャットまたは 1 Issue にコメント**でまとめ、**次のアクション**（誰が何をするか）を箇条書きにする。繰り返し使う型は **`RULES-INDEX.md` に日付＋1 行**で「パトロールの決めごと」があれば残す。

**関連**: GitHub 連携の索引は **`docs/claude-github-index.md`**。

## セッション開始時の作法（推奨・儀式）

### 既定：プロジェクト全体 Health Check（4 ステップ標準フロー）

**本リポの運用**: **新しい会話セッション**で **kintone 関連の実装・デプロイ・スクリプト・customize** に着手する**前**に、**毎回の明示依頼なしに**次を行う。

1. **Health Check** … **`環境整合性のチェック` の「プロジェクト全体の健康診断」**に従い、**全対象 appId**（`kintone-apps.md`・`customize/`・権限で取れる範囲）の**実フォーム**と **`kintone-apps.md`** を突合する。  
2. **Plan of Action** … ズレ・未取得 app・`.env` 不足などを**箇条書きで宣言**してから、**一括で正本追記・`app:types` 同期**（必要な app のみ）を行う。  
3. **エビデンス** … **`<details>`** に **実行ログの要約**（どの `app:fields` / `app:types` を回したか、終了コード、主な stderr/stdout の要点）。**レコードを更新しない**健康診断では **実データ JSON は「該当なし」** と明記。**レコードを触った**ときは **ビフォー／アフター**を従来どおり。  
4. **黄金 3 ステップ** … メインで**一言・変化・確認依頼**を書き、続けてユーザーの**本題（依頼された実装）**に入る（健康診断だけで終わる場合はその旨を**一言で**書く）。

**省略してよい**: **同一セッションの続き**のメッセージのみ・**純ドキュメント／ルール文面のみ**の編集・ユーザーが **「Health Check スキップ」** と明示・**`.env` 未設定で API が一切使えない**（その場合は **Plan of Action に未取得理由**を書き、`.env` 整備を依頼）。

### 復元チェックポイント（チャット履歴が無いとき）

**新セッション**で **実装・デプロイ・本番相当のスクリプト**に入る**前**に **`chat-sessions/checkpoint-latest.md`** を**読む**（**空・プレースホルダのみ**ならスキップ可）。ここは**作業文脈の補助**であり、**`.cursor/rules`・`kintone-apps.md`・本ファイルと矛盾する場合は常に正本を採用**する。運用の全文・更新タイミング・アーカイブは **`docs/agent-restore-checkpoint.md`**。

**「忘れた」防止（エージェント）**: **未完了**・**正本変更／デプロイ**・**方針決定**・**ブロッカー**・**「あとで」**のいずれかがあるときは、**完了報告の直前**に **`checkpoint-latest.md` を更新したか**確認する。**恒久に効く決定**はチャットだけに残さず **`RULES-INDEX.md` 1 行**または該当正本へ（**セッション締め 3 点**・トリガー一覧は **`docs/agent-restore-checkpoint.md`「『忘れた』を防ぐ」**）。

### アプリ単位の儀式（人間向けコピペ）

ユーザーがアプリ固有の機能を依頼するとき、**最初の一文**に次を足すと準備が揃いやすい。

> アプリ ID **[XXX]** の機能を実装する。**まず `app:fields` と型定義（`types/kintone-[XXX].d.ts`）が最新か確認し、必要なら更新してから**着手して。

エージェント側の想定動作（**上記プロジェクト全体 Health Check のあと**、またはスキップ時）: **`kintone-apps.md`（履歴含む）を読む** → **`types/kintone-{appId}.d.ts` の有無・更新要否** → 必要なら **`npm run app:fields -- <appId> --markdown`** と **`npm run app:types -- <appId>`** を実行 → 差分があれば **`kintone-apps.md` に履歴追記** → 実装。

## Implementation Starter（コピペ用）

人間・エージェントどちらでも、セッションの最初にそのまま貼れるテンプレート（**エージェントは `セッション開始時の作法` のプロジェクト全体 Health Check を先に自律実行してよい**）。

```text
アプリ ID [ID] の実装をします。まず npm run app:types -- [ID] と npm run app:fields -- [ID] --markdown を実行して最新の定義を把握し、kintone-apps.md に変更履歴を追記してから、[実装内容] に着手してください。
```

- `[ID]` … 数値のアプリ ID（例: `594`）
- `[実装内容]` … 具体的なタスク（例: 「627 の印刷レイアウトに VPN 行を追加」）

`app:types` は **`.env` が無い／変数不足のときフェイルファスト**し、**次に何をすべきか**を標準エラーに出す。ルートに `.env` を置き、`app:fields` と同じ認証情報を入れてから再実行する。

## npm エイリアス（正本更新の導線）

| コマンド | 役割 |
|----------|------|
| `npm run app:fields -- <appId>` | プレビュー API でフィールド一覧（TSV）。 |
| `npm run app:fields -- <appId> --markdown` | 上記を **Markdown 表**（`kintone-apps.md` 追記向け）。サブテーブルは `親 > 子`。 |
| `npm run app:types -- <appId>` | **`@kintone/dts-gen`** で **`types/kintone-<appId>.d.ts`** を生成（`.env` の `KINTONE_BASE_URL`・認証・任意 Basic・ゲストを使用）。未反映フォームは **`--preview`** を付与。 |

※ `app:types` は **`scripts/app-types.js`** が CLI を組み立てる（シェルで `$KINTONE_BASE_URL` を直に展開しない）。トークン認証なら **`KINTONE_API_TOKEN`**。

## Schema Retrieval Priority (Strict)

1. **Types**: 次が存在すれば最優先で参照する（生成物を `types/` に置く運用を推奨）。
   - `types/kintone-{appId}.d.ts`  
   - （別配置の場合は `glob: **/kintone-{appId}.d.ts` で探索してよい。npm の `@types/*` パッケージ名と混同しないこと。）
2. **Docs**: `kintone-apps.md` を参照する。**履歴テーブルは末尾が新しい**ので、最新の変更行と、該当アプリの見出し・一覧をあわせて読む。
3. **Live**: 上記が無い・古い・矛盾しているときは **`npm run app:fields -- <appId>`** で現状を取得する。正本へ追記しやすい整形は **`npm run app:fields -- <appId> --markdown`**（Markdown 表＋取得時刻コメント）。

**CRITICAL**

- フィールドコードを**推測しない**。アプリ ID が特定できないときは **ユーザーに appId を確認**する。
- フォームを変えてからロジックを変えるときは、先に **Live（`npm run app:fields -- <appId> [--markdown]` と `npm run app:types -- <appId> [--preview]`）で定義を最新化**してから実装する習慣とする（人手の「後で更新」は漏れやすい）。

## File Specific Rules

- **`kintone-apps.md`**: **追記のみ**。履歴・以前の行を**削除しない**（`RULES-INDEX.md` の方針どおり）。
- **サブテーブル・グループ内フィールド**: 識別子は **`ParentCode > ChildCode`**（例: `pc_ledger_list > mail`）。`app:fields --markdown` も同じ表記で出す。
- **REST / クライアント**: 認証・baseUrl は **`utils/kintone-common.ts`** または既存 `scripts/` の `.env` パターンに合わせる。ルート **`.cursorrules`** に共通方針あり。

### `@kintone/rest-api-client` の自律的な活用（Node / スクリプト）

**可能であり推奨する。** ルート **`package.json` の devDependencies** に **`@kintone/rest-api-client`** が入っている（`npm install` 済みなら `import { KintoneRestAPIClient } from '@kintone/rest-api-client'` で利用可）。

- **新規の Node スクリプト**でレコード取得・追加・更新・クエリなど **kintone REST** が要るときは、生の `fetch` より **`@kintone/rest-api-client`** を**優先**して実装してよい（型・エラーハンドリングが揃いやすい）。  
- **認証・baseUrl** は既存どおり **`utils/kintone-common.ts`** または **`npx dotenv -e .env -e .env.proxy -- node ...`** 等の **`scripts/` 標準**に合わせる。**API トークンはリポジトリに直書きしない**（`.env` / CI Secrets）。  
- **ユーザーが短く依頼**（例:「このアプリのレコードを API で取って」）した場合、エージェントは **クライアント経由で自律的に**手順・コードを組み立ててよい。アプリ ID や権限が不明なときだけ **`kintone-apps.md` またはユーザーに確認**。  
- **GitHub Actions 上の Claude** でも、`npm ci` 後は同パッケージが入るため、ワークフロー内スクリプトから同様に使える（Secrets にトークンを渡す前提）。

## エラー時の自己解決ルール（デバッグスクリプト）

**狙い**: エラーが出たとき、**説明だけ求めて止まらず**、エージェントが**切り分け用の小さなスクリプトやコマンド**で原因に近づき、**修正まで持っていく**（ユーザーは技術判断に詳しくない前提と整合）。

### 必ず踏む順

1. **エラーを読む** … **標準エラー全文**・**終了コード**・スタックの**先頭**。**メッセージを読まず同じコマンドを繰り返さない**（既存の黄金のサイクルと同じ）。  
2. **最小再現に落とす** … 1 アプリ・1 操作・可能なら**読み取りのみ**など、**影響範囲が最小**の手順にする。  
3. **自分で検証する** … 次を**自律的に**使ってよい。  
   - **`scripts/debug-*.js`** … 短命でよい。先頭に「用途・削除予定 or 残す条件」をコメント。`npx dotenv -e .env -e .env.proxy -- node scripts/debug-....js` 等、既存の **`.env` パターン**に合わせる。  
   - **`@kintone/rest-api-client`** … 1 件 GET・フィールド一覧に近い API で**権限・URL・レスポンス形**を確認。  
   - **`npm run app:fields` / `app:types`** … スキーム・権限の切り分け。  
   - **MCP / Web** … 公式ドキュメント・既知 Issue（着手前の情報収集ルールと同じ）。  
4. **直す** … 恒久対応は**本番コード・設定・フェイルファスト文言**（例: `scripts/app-types.js` のエラーヒント）。  
5. **デバッグ残骸の整理** … 下記 **「一時ファイルのゴミ拾い」**に従う。  

### 一時ファイルのゴミ拾い（意思決定の履歴を汚さない）

**狙い**: **`debug-*.js`・`tmp-*.ts`・検証用ワンオフ**がリポジトリに残り、将来 **「これは何のファイルか」** でノイズになるのを防ぐ。

- **作業完了時（コミット前）**に、セッションで**新規作成した一時ファイルは原則削除**する。  
- **将来も使う**と判断したときだけ、**適切な置き場**へ移す（例: **`scripts/debug/`** … 無ければ作成してよい。または既存の **`scripts/`** 運用に合わせる）。ファイル先頭に **用途・入力前提・実行例・保守方針**をコメントする。  
- **残したファイル**は **`RULES-INDEX.md` に日付＋1 行**で**用途**を追記する（または該当 **README に 1 行**）。  
- **`git status`** で**見知らぬ新規ファイル**を確認し、誤コミットを防ぐ。  

### やってはいけないこと

- **本番の大量削除・全件更新**を、ユーザーの明示なしにスクリプトから実行する。  
- **トークン・パスワード・個人情報**をログ・コミット・チャットに出す。  
- **同じ失敗を 3 回以上**、仮説の更新なしに繰り返す → **方針を変える**か、**取り返しが重い**ならユーザーに**1 問に絞って**確認。  

### 副作用の予測（共通部品）

**`utils/`**・**`utils/kintone-common.ts`**・**複数箇所から import / require される `scripts/` 内の共有処理**を変えるときは、**grep・コードベース検索**で**利用箇所を洗い出し**、**他アプリ・他スクリプトがデグレしない**ことを確認してから完了とする（必要なら影響のあるディレクトリで **`npm run lint:customize`** や代表スクリプトを追加実行）。

### 作業完了報告の型（黄金の3ステップ・ビジネス優先）

**狙い**: 報告の**冒頭で技術詳細に沈まない**ようにし、**ユーザーが体験する変化**と**次に何をすべきか**を先に渡す。

**義務**: 作業完了・PR 説明・チャットのまとめでは、**次の3つをこの順でメインに書く**（**専門用語はメインに出さない**）。

| ステップ | 内容 |
|----------|------|
| **1. 一行サマリー（結論）** | **何をしたかを一言**。**極力短く**（**目安 15〜40 文字**。絵文字 1 個まで可。業務文脈で少し長くてもよいが、**前置き・謝罪の長文は別段落にしない**）。例: `✅ 宿泊費の50万円チェックを実装完了` |
| **2. ビフォー・アフター（変化点）** | **以前は**どうだったか → **今後は**どう変わったかを**対比**（**箇条書き**推奨）。例: 以前は上限なしで保存可能 → 今後は 50 万円超でエラー表示 |
| **3. あなたの次のアクション（判断の仰ぎ）** | **いまユーザーが取るべき行動**を**明示**（例: GitHub でマージ、kintone で動作確認、何もしなくてよい、次回セッションで続き、等） |

**専門用語禁止（メイン部分）と箇条書きの徹底**

- **メイン（上記 3 ステップ）**では、**メソッド名・REST パス・細かいファイル名の羅列**など**エンジニア向け細部は書かない**。**ユーザーが画面や運用で感じる変化**を優先する。  
- **図・箇条書き**を活用し、**冒頭から約 3 秒で要旨**が伝わるようにする。  
- **技術的な詳細**（触ったパス、コマンドログ、diff 要点、**PR 前セルフチェック**の自問結果、**Lessons Learned** のうちエンジニア向けのもの）は、**必ず下記テンプレートの `<details>` 内**にまとめる（メインに混ぜない）。

**証拠の提示（実証主義）**: 「直した」**だけ**で終わらせない。**`<details>技術的な詳細` の中**に、**実行したコマンド**の成功の要点（終了コード 0・stdout の要約）または**テスト結果**を書く。**まだ実行していない**場合は **「検証未実行」** と理由を** details か一行で**明示する。

**実データスナップショット（ビジュアル・デバッグ・不整合防止）**

**狙い**: 「動いたが**データが壊れていた**（不整合）」を防ぎ、画面を開かずに**実値で検証**できるようにする。

**次を満たす作業では必須**（該当しないときは details 内に **「レコード実データの差分なし（UI のみ・設定のみ等）」** と一行）:

- **レコードの追加・更新・計算フィールドの再計算トリガ**・一括スクリプト・API 連携で**レコード内容が変わる**可能性があるとき  

**`<details>技術的な詳細` 内**に、**代表的な 1 レコード**について **修正前・修正後**を**比較しやすい形**で載せる（**JSON 抜粋**でよい。**主要フィールドのみ**—全体コピペは不要）。**取得方法**は **GET 1 件**（`@kintone/rest-api-client`・既存スクリプト等）でよい。

- **個人名・メール・電話・住所**などは **`***` 等でマスク**する。**トークン・パスワードは絶対に貼らない**。  
- **本番に触れず検証できた**場合はその旨を書く。**実データを取得できなかった**場合は **「実データ未取得」** と**理由**（権限・sandbox なし・読み取りのみ未実施等）を必ず書く。

#### 報告テンプレート（この通りに書く）

エージェントは **コピペ用**として次を使い、**見出しと `<details>` 構造を維持**する（チャットでも PR 本文でも可）。

```markdown
### 📢 作業完了のご報告

- **一言で**: [ここに結論]
- **変わったこと**:
  - **以前**: ◯◯ だった / ◯◯ ができなかった
  - **今後**: ◯◯ ができるようになり、△△ のミスを防げます
- **確認のお願い**: [いまあなたがしてほしいこと]

---

<details>
<summary>🛠️ 技術的な詳細（エンジニア向け）</summary>

- 変更したファイル・設定の要点
- 実行コマンドと結果（終了コード・要約）／**検証未実行**の場合はその理由

- Lessons Learned（再利用価値の高い事実。メイン向けの一文に要約済みならここは短くてよい）

</details>
```

**`<details>` が使えない UI**（一部チャット）では、**`---` の直後**に見出し **`### 🛠️ 技術的な詳細（エンジニア向け）`** を置き、同じ内容を**その下にそのまま**書く（折りたたみなし）。

### PR 作成前のセルフチェック（セルフ・コードレビュー）

**狙い**: 人間が行間まで読まなくても、エージェント自身が **kintone 向けのアンチパターン**と**運用リスク**を一度通す（**兼ねる QA**）。

**PR を出す直前**（または「PR 相当」の変更をまとめて報告するとき）、次を**自問自答**し、**結論を報告に箇条書きで含める**（該当なしなら「該当なし」と書く）。

| 観点 | 自問の例 |
|------|----------|
| **API の同時実行・レート** | ループや `Promise.all` で **同時に飛ばすリクエスト数**は、kintone の**制限・429・Bulk / 一括 API の仕様**に収まっているか。必要なら**直列化・バッチ・待機**を入れたか。 |
| **保守性・密結合** | アプリ ID・フィールドコードが**あちこちにハードコード**されていないか（**`kintone-common`・定数・正本**に寄せられるか）。**イベントハンドラが肥大化**していないか。**ルックアップ／依存マップ**と矛盾する参照はないか。 |
| **正本との整合** | 触ったアプリは **`kintone-apps.md`（依存マップ含む）**・**生成型**と**食い違っていない**か。 |
| **レコード実データ** | **更新・計算・一括処理**が絡むとき、**API 等で実測した**代表的 1 件の**主要フィールド**について **before / after** を報告 **details** に載せたか（**不整合の早期発見**）。該当なしなら「データ差分なし」と明示したか。 |

**見つかった懸念**は PR 本文またはチャットに**正直に書く**（隠さない）。**軽微ならその PR で直す**、**大きいなら別 Issue に切る**かユーザーに一言する。**記載場所**は **報告テンプレートの `<details>技術的な詳細` 内**を正とする（メインに技術表を貼らない）。

### 作業完了時（Lessons Learned・暗黙知の明示化）

**Lessons Learned** は**箇条書きで 1〜3 個**まで（無ければ「なし」）。**置き場所**は **`<details>技術的な詳細` の中**、またはその直後の短い見出し（**メインの「一言で」以下には載せず**、業務向けに要約する場合は **一言で** に**一行だけ**反映してよい）。

- **書く内容の例**: 未知エラーの**解き方**、特定 **kintone API / CB_* / GAIA_*** の実測挙動、**grep で見つけた依存**、**下次第〇アプリも見る**と決めたこと。  
- **新しく判明した事実**で**再利用価値が高い**ものは、チャットだけに留めず **`RULES-INDEX.md` に日付＋1 行**を必ず足す。必要なら **`kintone-apps.md`**（依存マップ・注記）や **`scripts/app-types.js`** のメッセージ、**`.cursor/rules/*.mdc`** に**1 行**反映する。  
- **狙い**: 「過去の自分」＝**正本**から次のセッションが学べる**自己進化ループ**（チャットの暗記に頼らない）。

### ナレッジ化

**新しいエラーパターン**を解いたら、**`RULES-INDEX.md` に日付＋1 行**（上記 Lessons Learned と**統合してよい**）。**繰り返し起きる kintone コード**は `app-types.js` 等の**ユーザー向けメッセージ**や **`kintone-apps.md` の注記**に反映を検討する。

## kintone 開発の「黄金のサイクル」（チーム共有・備忘録）

**狙い**: 「AI に考えさせる」だけにせず、**失敗した瞬間に次のアクション**（`.env` の用意・変数の補充・正しい実行コマンド）が**コード（フェイルファスト）とドキュメントの両方**から読み取れるようにし、**迷走を遮断**する。

1. **儀式の実行**  
   **Implementation Starter（コピペ用）**を Claude Code に渡し、**対象アプリ ID** と **実装内容**をはっきり書く。

2. **自動環境チェック**  
   **`npm run app:types -- <ID>`** が先に動く。認証や base URL が無ければ **`scripts/app-types.js`** が **具体的手順つきで終了**するので、エージェントは **「.env を用意し、このキーを埋めて再実行」** とユーザーへ要求しやすい（理由不明なループを抑止）。

3. **スキーマの同期**  
   環境が揃えば **`types/kintone-<ID>.d.ts`** が生成され、あわせて **`npm run app:fields -- <ID> --markdown`** で **`kintone-apps.md` に貼る用のスナップショット**が得られる。**履歴を追記**すると、エージェントの参照する**真実のソース（型＋MD）**が揃う。

4. **安全な実装**  
   型（生成 `.d.ts`）・**`kintone-apps.md`（末尾が新しい履歴）**・**`kintone-schema-trust.mdc`** に沿い、**フィールドコードを推測しない**コードに落とす。

### 運用を伸ばすとき

特定の**プラグイン環境**・**複雑なルックアップ階層**・**社内の命名規則**でエージェントが迷いがちになったら、都度コードを増やさず **`.cursor/rules/kintone-schema-trust.mdc` にルールを 1 行足す**だけで追補できる（正本はあくまで **`CLAUDE.md`** の優先順位と整合させる）。

### ルールの継ぎ足し時（運用でこう見えたら）

サブテーブル集計などは **`Parent > Child`** が `app:fields --markdown` と `kintone-apps.md` に揃っていれば、**`map` / `reduce` の対象キー**を AI が取り違えにくい。

次のような挙動が出たら、そのログ・**アプリ ID**・直前のコマンドを共有し、ルールかフェイルファスト文言を研ぐ。

| 兆候 | 打ち手の例 |
|------|------------|
| **型（`types/kintone-{id}.d.ts`）があるのに古いフィールド名を書こうとする** | **`kintone-schema-trust.mdc`** で「型を開いたうえで `grep`」「`kintone-apps.md` 履歴末尾優先」を**1 行強化**。別名→現行コードの表を `kintone-apps.md` に追記。 |
| **API トークン権限不足などで `app:types` が失敗し、同じコマンドをリトライし続ける** | **`scripts/app-types.js`** の終了前に **kintone エラーコード／代表的メッセージ**を検知し、「トークンにアプリ閲覧が付いているか」「パスワード認証に切り替え可能か」を**標準エラーで明示**（パターンは運用で追記）。 |

**フィードバック歓迎**: 「アプリ **ID** で **こういうバリデーション**を追加しようとしたら **こう動いた**」とログをもらえれば、上表を具体化して再研ぎできる。

### 運用フェーズで共有すると効く材料（優先度高）

kintone API の **`CB_*` / `GAIA_*` などは実測が最優先**。改善の材料として、次を残せると **ルール・フェイルファスト・MDC** の追記が速い。

| 残すもの | 用途 |
|----------|------|
| **Claude Code の思考（Thought）** | 儀式スキップ・正本を読まずに推測に逃げた経路の特定 |
| **ターミナル実行ログ**（`app:types` / `app:fields` の**全文**、終了コード） | 権限エラー等の **実メッセージ** を `app-types.js` のパターン検知に転記するため |

典型的な「次の研ぎどころ」（実タスク後のチェックリストのイメージ）:

- **儀式**（コピペテンプレ・`app:types` / `app:fields`）を飛ばしてすぐ実装に入った。
- **`app:types` の stderr を読まず**に同一コマンドをリトライした（**CB_AU01 / GAIA_IL02 等はログごと共有**されると助かる）。
- **サブテーブル**で `record[親].value` の**行要素**を経由せず、一階層飛ばしで子フィールドへ触ろうとして型／実行時エラーになった。

### ログ共有時のアップデート方針（運用契約）

実ログ（**Thought + ターミナル**）を投げてもらったら、その内容に応じて開発環境を都度アップデートする。以下は Claude Code との共同作業における **PDCA**（共有 → ルール／コード改修 → 再実行）の置き場の約束として扱う。**対応の置き場**は次のとおり。

| 違和感・エラー | 主な手当て |
|----------------|------------|
| **`CB_*` / `GAIA_*` など kintone のエラー** | **`scripts/app-types.js`** のフェイルファストに**実測パターン**を追加し、「権限か・トークンか・別認証に切り替えよ」など**即答できる一文**を標準エラーに載せる。 |
| **階層の読み飛ばし**（Thought で子フィールドに直接触れようとしている等） | **`.cursor/rules/kintone-schema-trust.mdc`** を具体化（例: `table.value.forEach` / `reduce` の形を例示する 1 行）。 |
| **「儀式」の形骸化**（定義更新をサボる） | **`CLAUDE.md`** の優先順位・黄金のサイクルを**強制ステップ**に近い表現へ改稿（必須コマンド・順序の明示）。 |
