# 入社・異動・退社の運用（社員マスタ／アカウント台帳／PC台帳）

フィールドコードやアプリ ID の正本は **`kintone-apps.md`**。ここでは手順とシステム連動の観点だけをまとめる。

## 関係アプリの役割（整理）

| 論理 | アプリ ID | 役割 |
|------|-----------|------|
| 社員マスタ | 595 | 人事起点の正（氏名・所属・メール・在籍・退職日など） |
| アカウント管理台帳 | 627 | アカウント情報・在籍・**アカウント状態**（主キーは **メール**） |
| PC 台帳 | 594 | 端末と利用者（**メール**で人と紐づく） |
| アカウント採番 | 626 | 627 新規登録時に使うプール（ログオン・各種パスワード等） |

595 に **台帳レコード番号（`ledger_record_id`）** と **台帳作成済み（`ledger_created`）** がある場合、保存後の 627 連動ではその **627 の $id** を優先して更新する（**627 専用**。PC 台帳とは別）。

**PC 台帳（594）** は 1 人で複数台あり得るため、595 のサブテーブル **`pc_ledger_list`**（子: **`pc_594_record_id`**＝594 の `$id`、**`pc_ledger_entry_done`**＝作成済み）で紐づける。594 を保存するか PC買替で新規 594 ができると、同一 `mail` の 595 に行が足り **`作成済み` が自動で付く**（ブックマーク用リンクは 595 詳細に表示）。**PC買替（リンクの付け替え）**では、旧 594 を廃止するときに **`mail` を空**にし、595 の **`pc_ledger_list` から旧 594 の `$id` 行だけ削除**したうえで、**新 594 の `$id` を同じ利用者 `mail` の 595 に追加**する（退職時の UI 非表示のみとは別経路で、データ上は必ず付け替える）。既存レコードのまとめ足しは `npm run backfill:595:pc_ledger_from_594`。

## 入社

1. **595** にレコードを登録する（必須：`mail`、氏名・所属・グループ・在籍など）。メールは **627・594 と同一人物で共通**にする。
2. **627**  
   - 運用に合わせて「新規レコード」を作成する。画面カスタマイズでは、**595 と 626** から自動入力する流れを想定している（詳細は `customize/627/desktop.js`）。  
   - 運用で 595 に **627 のレコード番号**を載せる場合は、`ledger_record_id` 等を登録する。
3. **594**  
   - 端末を割り当てたら PC 台帳に登録し、**利用者の `mail`** を正しく入れる。
4. **626**  
   - 新規アカウントに採番プールを使う場合は、運用ルールどおり **使用済み**などのフラグを更新する。

※ 一括やバッチ連携を使う場合は `npm run sync:595` 等（`package.json` 参照）の前提を確認する。

---

## 異動

1. **595** で **所属名・所属グループ・社員名**を直し、必要なら **メール変更**も行い、**保存**する。
2. **保存成功後の自動連動**（`customize/595/desktop.js`）  
   - **627**：同一 `mail` の 1 件を更新（`ledger_record_id` があればそれを優先）。所属・氏名に加え、在籍と **アカウント状態**も 595 の内容（退職日・在籍ステータス）に合わせて更新する。  
     - ただし **627 の `account_state` が「削除」** の行は、**在籍・アカウント状態だけ更新しない**（所属・氏名のみ反映）。  
   - **594**：同一 `mail` の **すべての行** に、所属・グループ・**利用者名**を反映する。  
     - ただし **退職者対応**として、`status` が **廃棄・除却・廃止**を含む、または **`abolished_flag` に「廃止」** がある行は **触らない**（現場がステータスで済ませた端末を上書きしない）。
3. **メールを変更した異動**では、627・594 側の旧メールのレコードをどう扱うか（**同一人物の移行**か、**別人の再利用**か）を運用で決め、**手で整合**する。自動連動は「保存した 595 行の `mail`」に紐づく 627/594 だけが対象になる。

---

## 退社（退職）

1. **595** に **退職日**を入れ、在籍ステータスを **退職** にする（運用どおり）。保存する。
2. **627**  
   - 上記と同じ保存後連動で、627 は **在籍・アカウント状態が退職扱い**に揃う（`account_state` が **「削除」** の行は在籍・アカウント状態は除外、という条件は異動と同じ）。
3. **594（PC 台帳）**  
   - **登録者**が、退職に伴う **利用者変更・廃棄**に応じて、各 PC レコードの **`status` や `abolished_flag`** を更新する。  
   - **すでに廃棄・廃止扱いにした行**は、595 の保存だけでは **所属・利用者名を上書きされない**。  
   - **退職日が入っている**とき、**廃棄・廃止行以外**の 594 について、記事欄へ **退職者利用分の追記**が入る（重複行は追記しない実装）。
4. **退職者**については **627・594 へのクイックリンクを画面カスタマイズで出さない**（データ上の `mail` や `ledger_*` は残り得る。`mail` 必須との整合を API で解決する必要はない）。編集画面では **在籍ステータス・退職日**の変更時にリンク枠を付け直すため、保存前でも概ね直ちに非表示になる。
5. 退職後も **履歴として残す 627 / 594** の扱いは、別途ガイドライン（棚卸・削除アカウント状態など）に従う。

---

## 権限・API

595 を保存して連動させるユーザーには、**627 と 594 のレコード更新権限**が必要。不足すると API が失敗し、画面にエラーが出る。
