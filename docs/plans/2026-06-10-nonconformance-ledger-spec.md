## §4. 管理番号採番 — **自動（案 A 確定・2026-06-10 浜田）**

Excel 説明文: `[西暦4桁]－[その年の通し番号3桁]`（例: 2026 年 1 件目 → `2026-001`）。

**確定**: **YYYY = 報告日の西暦** / NNN = その年の通し 3 桁（001〜999）/ **完全自動**。

### 4.1 共通（自動採番の前提）

| ルール | 内容 |
|--------|------|
| **形式** | `{YYYY}-{NNN}` — `YYYY` 4 桁、`NNN` **3 桁ゼロ埋め**（001〜999） |
| **付与タイミング** | **新規保存の直前**（ダッシュ JS が REST 前に採番） |
| **手入力** | **不可**（UI に入力欄を出さない） |
| **変更** | **一度付与した番号は変更しない**（後から報告日を直しても番号は据え置き） |
| **削除** | 誤登録削除しても **欠番は埋めない**（`2026-002` 削除後も次は `2026-003`） |
| **上限** | 年 999 件超 → エラー表示（想定外・推進室へ連絡） |

### 4.2 「その年」の取り方 — **相談ポイント**

| 案 | YYYY の決め方 | メリット | デメリット |
|----|---------------|----------|------------|
| **A（推奨）** | **報告日**の西暦 | 事象の年と番号が一致。遅れて入力しても **報告日を過去にすれば** その年の連番になる | 報告日を間違えると番号の年もズレる（番号は後から直せない） |
| **B** | **登録日（保存した日）**の西暦 | 実装が単純。「今年の何件目」が一目 | 数ヶ月前の事象を後から登録すると **番号の年が実態とズレる** |
| **C** | **常に当年**（= B と同義だが報告日無視） | — | 台帳としての年次整理に向かない |

**CIO 推奨: 案 A（報告日基準）** — Excel の「その年の通し番号」を **事象の報告日の年** と解釈するのが自然。ダッシュ default 報告日=**今日**なので、通常入力は「今年の連番」になる。

### 4.3 採番アルゴリズム（案 A 確定時）

1. ユーザーが新規フォームで **報告日**（default 今日 JST）を確認・必要なら変更  
2. `YYYY` = 報告日の西暦  
3. DB を `mgmt_no` **降順**でクエリし、`YYYY-` で始まる最大 NNN を取得  
4. 次番 = `NNN + 1`（無ければ `001`）→ `mgmt_no = "{YYYY}-{NNN:03d}"`  
5. POST（同時登録対策: 409/重複時は **1 回だけ**再採番）

### 4.4 運用例（案 A）

| 操作 | 結果 |
|------|------|
| 2026-06-10 に今日の事象を登録 | 報告日 2026-06-10 → **`2026-001`**（当年初件） |
| 同日 2 件目 | **`2026-002`** |
| 2026-06-10 に **2025 年の事象**を遡及登録（報告日を 2025-11-01 に変更して保存） | **`2025-001`**（2025 年枠の連番。2025 年に既に 1 件あれば `2025-002`） |
| 登録後に報告日だけ修正 | **管理番号は変わらない** |

### 4.5 確定

- **案 A（報告日基準）** — 浜田 2026-06-10 OK

## §5. ダッシュ UI 要件 — **Excel 並みの簡単入力（v1 最優先）**

> 参照実装: `customize/shared-mail-dash/desktop.js`（696）— 表一覧 + モーダル CRUD。本案件は **列が Excel と同型**なので **より表に近い UI** を目指す。

### 5.1 画面構成

| 領域 | 内容 |
|------|------|
| **ヘッダ** | タイトル「不適合管理台帳」・**＋行を追加**（主ボタン）・検索ボックス |
| **一覧** | **Excel 風の表** — 10 列を横スクロール可で一覧表示（管理番号〜確認者） |
| **操作列** | 各行に **編集** / **削除**（誤登録のみ） |

### 5.2 入力の簡単さ（浜田要望）

| 要件 | 実装方針 |
|------|----------|
| **1 行 = 1 不適合** | Excel と同じ感覚。複雑なウィザードなし |
| **新規** | 「行を追加」→ **1 画面の入力フォーム**（モーダル）。保存で一覧に即反映 |
| **自動で埋める** | `mgmt_no` **自動** / `report_date` **今日（JST）** を default |
| **手で打つ** | 報告者・種別・4 つの本文（内容/原因/暫定/恒久）・確認者 |
| **種別** | ドロップダウン 3 択（Excel の A/B/C と同ラベル） |
| **完了** | `completed_date` は **空でも保存可**（後から編集で追記） |
| **編集** | 行の「編集」→ 同じフォーム。Excel の行修正と同様 |
| **kintone 標準** | DB アプリの **追加・編集・保存ボタンは使わせない**（695/693 型ブロック） |

### 5.3 一覧の見え方

| 機能 | 内容 |
|------|------|
| ソート | 管理番号・報告日（新しい順 default） |
| フィルタ | 種別 A/B/C / **未完了**（完了日が空） |
| 検索 | 管理番号・報告者・ミスの内容（部分一致） |
| 長文 | 一覧では **先頭 1 行だけ**表示。全文は編集モーダル |

### 5.4 v1 で省略可

| 項目 | 方針 |
|------|------|
| 印刷 | 後回し可（Q7） |
| ユーザー選択フィールド | 使わない（文字列の方が Excel に近い） |
| Excel インポート | 初回 **0 件** — サンプル行は移行しない |

### 5.5 権限（2026-06-10 浜田 — **(B) 確定**）

| 区分 | 方針 |
|------|------|
| **入力・編集** | **システム推進室メンバー複数** — ダッシュから行の追加・編集・削除 |
| **報告者・確認者** | **文字列手入力**（誰が起票しても名前を自由記入） |
| **DB アプリ標準 UI** | 推進室 = **閲覧のみ**（保存・削除ボタンは JS でブロック — 695 型） |
| **ダッシュ** | 推進室 = **利用可**（日常入口） |
| **REST 書込** | ダッシュ JS が **ログインユーザーの権限**で DB に POST/PUT/DELETE（696 型） |
| **DB アプリ権限** | 推進室グループに **レコード追加・編集・削除** を付与（標準 UI は使わせないが API 用） |
| **他部署** | v1 = **アクセスなし**（Space 48 内リンクも推進室向け） |

**Space 48 thread**: **52** を想定（682/701 同型 — 作成時に指定。変更あれば §41）。
