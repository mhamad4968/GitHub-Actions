## 2. アーキテクチャ候補（明日朝にユーザーへ確認したい）

### 候補A: SKYSEA 自身の「リモートインストール」機能を活用
- SKYSEA 管理機側に「未受信端末リスト」と「リモートインストール」機能あり（Sky 標準）
- 一覧→選択→配布が一番素直で安全
- 必要: 管理機の権限・現状の運用ルール確認

### 候補B: AD (Active Directory) GPO ソフトウェアインストール
- コンピュータ構成 → ソフトウェアインストール（MSI 割り当て）
- 既定では **次回起動時** 適用 → 「起動中に入れたい」要件にミスマッチ
- ログオンスクリプト方式にすればオンライン中も実行可だが、ログオン待ちが発生

### 候補C: スクリプト＋WinRM (PowerShell Remoting)
- 管理サーバから `Invoke-Command -ComputerName <PC> -FilePath install-skysea.ps1`
- **起動中の端末に即時配信可能**（要件に合致）
- 必要: ドメイン管理者権限 / WinRM(5985/5986) 開放 / Defender ASR 例外
- インストール元: 共有フォルダ `\\fileserver\skysea$\SkySetup.msi` 等

### 候補D: PsExec
- `psexec \\PC -s -d msiexec /i \\share\SkySetup.msi /qn`
- 軽量だが Defender がブロックすることが増えている

### 候補E: Intune / SCCM
- 既存導入があるなら最も筋が良い。なければ今回は対象外

## 6. リスク・注意点（先に共有しておきたい）

- **WinRM プッシュインストール**は AV/EDR から「ラテラルムーブメント」として誤検知されやすい。事前に Defender ASR 除外申請が必要なことが多い。
- **再起動を伴うインストール**は業務中だと事故になるため、SKYSEA は無人インストールでも「**バックグラウンドで完了 → 次回起動時にサービス開始**」のオプション運用が安全。
- **失敗ログ収集**を最初から仕込むこと（端末名・時刻・MSI終了コード）。
- 既に kintone 側には **PC1台に複数アカウント** や **同一 ledger_record_id 重複** があり、PC_name の一意性の前提に注意。
- **【重要・2026-04-19 追加】社員に気付かれずに配信したい** という運用要件あり。以下のとおり整理（2026-04-19 浜田判断確定）:
  - a. インストール中にポップアップ・ダイアログ出さない → ❌ **必須ガード**（`/qn` サイレント引数）
  - b. デスクトップアイコン作らない → ❌ **必須ガード**
  - c. タスクトレイ常駐アイコン → ⭕ **出てもOK**（SKYSEA 仕様上やむなし）
  - d. PC 再起動を要求しない → ❌ **必須ガード**（`/norestart` + バックグラウンド完了）
  - e. インストール完了後にバルーン通知・トースト通知出さない → ❌ **必須ガード**
  - f. 「プログラムの追加と削除」一覧表示 → ⭕ Windows 仕様で必ず出る（仕方なし）
  - → 業務時間中の配信でも a/b/d/e がガードされていれば、社員は「いつの間にか入ってた」状態になる
  - → A 方式（SKYSEA 標準）なら管理機の配信設定で a/b/d/e を一括制御できる利点あり

## 7.5 推奨アーキテクチャ（2026-04-19 確定 / 浜田と詰めた最終版）

> 浜田の最重要要件 = **「確実に管理したい」+ 社員に気付かれない (a/b/d/e ガード) + バッチ運用**

### 2026-04 時点の採用案: **C-2 + C-3 ハイブリッド**（8月は SKYSEA 標準機能を第一候補に再評価）

#### kintone 674 に実装済みのフィールド (4 つ)

| フィールド | 型 | 用途 |
|---|---|---|
| `skysea_status` | DROP_DOWN | 未確認 / 配信予定 / 導入済 / 失敗 / 対象外 |
| `skysea_checked_at` | DATETIME | 最終確認時刻（バッチが自動更新）|
| `skysea_install_log` | MULTI_LINE_TEXT | 失敗理由・MSI 終了コード等 |
| `skysea_target_flag` | CHECK_BOX | 「次回配信対象」（浜田が手動チェック）|

#### 運用フロー

```
[毎日朝 06:00 cron] 状況同期バッチ (補助スクリプト)
  └─ SKYSEA 管理機の現状 → kintone 674 の個人PCと突合
  └─ skysea_status を更新 (未導入 PC は「未確認」に)

[浜田の確認作業 / kintone 674]
  └─ 検索パネル「📌 SKYSEA 未確認」トグル → 候補一覧
  └─ 一覧から「これは配信」「これは対象外（廃却済等）」を判断
  └─ 配信したい PC に skysea_target_flag をチェック

[毎晩 22:00 cron] 配信バッチ (C-2: PowerShell + WinRM)
  └─ kintone 674 から「skysea_target_flag=ON」の個人 PC リストを取得
  └─ 各 PC に WinRM で配信 (並列 3 件ずつ・a/b/d/e 全ガードの引数で)
  └─ 結果を kintone 674 に書き戻し (status / log / checked_at)
  └─ 失敗は翌晩リトライ (3 回まで)

[GPO 起動スクリプト・C-3] ← 安全網
  └─ 配信漏れの PC が翌朝起動時に SYSTEM 権限で自動インストール
  └─ 今後新規 PC が AD に参加した瞬間にも自動配信 = 永続運用
```

#### 確実性を支える 5 つの仕組み

| # | 仕組み | 効果 |
|---|---|---|
| 1 | **配信前承認**: 浜田が kintone でレビューしてから配信 | 暴走防止・誤配信ゼロ |
| 2 | **状況自動同期**: 朝 cron で SKYSEA → kintone 反映 | 進捗が一元可視化 |
| 3 | **段階展開**: target_flag 一括 ON じゃなく段階的に | リスク最小化 |
| 4 | **自動リトライ**: 失敗時に翌晩自動再配信 (3 回) | 一時的なエラー自動解決 |
| 5 | **C-3 安全網**: C-2 で漏れても起動時に自動 | 取りこぼしゼロ + 永続運用 |

### 方式 A (SKYSEA 標準のリモートインストール) の位置づけ

- C-2 + C-3 ハイブリッドで自前実装する方針が確定したため、**A は補助的に使用**
- A の「未受信端末リスト CSV エクスポート」だけは活用したい (Q1 で確認)
- 本配信は C-2 (バッチ) 中心

```
[1] SKYSEA 管理機で配信
    └─ 未受信端末リストから選択 → リモートインストール
       (a/b/d/e ガード設定で社員に気付かせず配信)

[2] 配信結果を kintone 674 に反映（補助スクリプト。自動化範囲は8月に決定）
    skysea-recon.mjs を発展させる
    └─ SKYSEA 管理機 CSV エクスポート → kintone 674 の個人PCと突合 → 各 PC の status 更新
        - skysea_status: 「導入済」「未導入」「失敗」「対象外」
        - skysea_checked_at: 最終確認時刻
        - skysea_install_log: 失敗理由 (MSI 終了コード等)

[3] kintone 674 で「SKYSEA 未導入」を絞り込み → 残りの未導入 PC を確認

[4] 失敗 PC は SKYSEA 管理機で再配信 (3 回までリトライ)

[5] 3 回失敗した PC は kintone 通知 / メール → 浜田が手動対応
```

### 確実性を支える 5 つの仕組み

| # | 仕組み | 効果 |
|---|---|---|
| 1 | 配信前チェック: 既存 158 台には配信しない（SKYSEA 標準が自動除外）| 二重インストール防止 |
| 2 | 配信結果の反映: SKYSEA → kintone 674 | 進捗が一元可視化 |
| 3 | 未導入 PC のフィルタ: 674 の SKYSEA 項目で絞り込み | 残り何台か即把握 |
| 4 | 失敗時の自動リトライ: SKYSEA 管理機の再配信スケジュール（3 回まで）| 一時的なエラーは自動解決 |
| 5 | 3 回失敗の通知: kintone 通知 or メール | 放置されない |

### 方式 C (PowerShell + WinRM) の位置づけ

- **A の機能不足時のフォールバック**として温存
- A が「未受信端末リスト」「リモートインストール」「サイレント運用設定」のいずれか欠ける場合に検討
- Q3 (AD)・Q4 (WinRM) は C のための情報なので「重要度下げ」だが念のため聞く

### 11.4 配信方式

- 第一候補は SKYSEA標準リモートインストール機能。管理画面に該当メニューを見た記憶はないが、契約・オプションを含めてSKY社回答まで「機能なし」と断定しない。
- 標準機能で要件を満たさない場合の確定フォールバックは、**新規専用GPO + SYSTEM権限のスケジュールタスク**。
- 既存GPOは変更しない。SKYSEA配信用GPOを新規作成するため、既存GPOバックアップは必須としない。
- 承認済みPCだけを入れる **専用ADセキュリティグループ**を作る。
- PCは通常OUから移動しない。OUが分かれていても本施策のために再編しない。
- GPOは専用グループへのセキュリティフィルタで限定する。
- GPO反映は通常のグループポリシー更新を待ち、`gpupdate /force` は行わない。
- ADグループ・GPOの操作は **浜田が実施**。AIチームは手順、PowerShell、確認方法を作成する。
- 管理処理（候補生成、AD追加案、CSV突合、App 674更新）は完全自動にせず、毎回浜田がAIチームへ実行を指示したときだけ行う。

### 11.5 実行日時・負荷制御

- 実行曜日: **火曜〜木曜のみ**。
- 月曜、金曜、土曜、日曜、**日本の祝日**は配信しない。
- 実行時間帯: **10:00〜17:00**。始業8:30直後は避ける。
- 接続待ちPCは時間帯内で **1時間ごと**に確認する。
- 同時実行は初期値 **最大5台**、かつ **同一拠点は同時1台まで**。
- AIチームが試験結果、失敗率、ネットワーク負荷を見て段階展開台数を判断する。
- 段階の基本案は試験1台から開始し、小規模→中規模→残りへ拡大する。
- システム推進室PCは管理端末のため試験対象にしない。浜田が「社内LANへ確実に接続中の未導入PC」を指定する。
- 試験PCの利用者へ事前通知しない。

### 11.6 インストーラー・共有フォルダー

- インストーラーは共有サーバー上に配置済み／配置予定。
- ファイル容量: **101MB（106,562,304バイト）**。
- 配布用フォルダー権限:
  - `Domain Computers`: 読み取りのみ
  - 管理者: 書き込み可
  - `Everyone` の広い権限は使用しない
- フォルダー作成・権限設定は浜田が実施し、AIチームが具体手順を案内する。
- インストーラーは共有上から直接実行せず、PCの一時フォルダーへコピーする。
- 配布前に正規ファイルの **SHA-256** を記録し、各PCでコピー後に一致確認する。
- ハッシュ不一致時は全体停止する。
- 成功・失敗にかかわらず、必要なログ保存後にPC上の101MBファイルを削除する。
- 管理機バージョンとの対応が確認できない古いインストーラーは配布しない。

### 11.7 実行前条件

- SKYSEAサービス名、インストール先、Windowsのアプリ登録名は、導入済みPC1台から読み取り確認して二重導入防止に使う。
- 実行条件:
  - Windows 11 Pro / Intel・AMD 64bit
  - AD参加済み
  - 会社LANへ接続中
  - AC電源接続中、またはバッテリー残量50%以上
  - Cドライブ空き1GB以上
  - Windows Update等の再起動待ちでない
- AD不在は自動配信せず確認一覧へ出す。必要なAD参加作業は浜田が行う。
- 再起動待ちPCは浜田へ一覧提示し、アップデート・再起動完了後の別日に再試行する。
- マカフィ導入済みで、Defenderも有効表示。実際のアクティブ／パッシブ状態は試験PCで確認する。
- マカフィ管理コンソールで検知・隔離ログ確認と設定変更が可能。
- セキュリティ除外は最初から設定しない。正規インストーラーが遮断された場合だけ、対象ファイル・パス・期間を限定して設定する。

### 11.8 サイレント・再起動・タイムアウト

- ポップアップ、ダイアログ、トースト、完了通知、デスクトップアイコン作成を抑止する。
- タスクトレイアイコンと「インストール済みアプリ」への表示は許容する。
- 強制再起動は行わない。通常の手動導入では再起動要求は出ていないが、安全ガードは維持する。
- 再起動が必要な場合はその場で実行せず、次回の通常再起動で有効化する。
- インストール上限時間は **30分**。
- 30分超過時は新規配信を停止し、原因確認する。インストーラープロセスを直ちに強制終了しない。
- 強制再起動、業務画面への通知、PC動作不良、想定外PCへの配信のいずれか1件でも発生したら **全体停止**し、原因究明後に再開する。
- 全体停止スイッチを必須とする。

### 11.9 再試行・例外

- 未接続PCは失敗回数に含めず、接続待ちとして継続する。
- 接続できたがインストールに失敗した場合は最大 **3回**。
- 3回失敗後は自動再試行を止め、要確認一覧へ移す。個別通知は出さない。
- どうしても導入できないPCは、浜田が現地訪問時対応を判断する。
- インストール実行後、SKYSEA管理台帳への反映を **24時間**待つ。その間は再配信しない。
- 導入済みだったPCが後日のSKYSEA CSVから消えた場合、自動で「未導入」へ戻さず **要確認・再試行候補**とする。
- 試験PCで問題が出た場合は、SKY社の正式手順に従い、そのPCだけアンインストールして復旧する。

### 11.10 CSV突合・App 674更新

- 浜田がSKYSEA管理台帳の **全件CSV**を提供する。
- AIチームはPC名、導入状態、最終通信日時、クライアントバージョン等の必要列だけを使用する。
- 元CSVはGitへ登録せず、リポジトリ外の保護フォルダーで管理し、完了後3か月で削除する。
- App 674の更新は、配信コマンド成功だけでは「インストール済み」にしない。
- SKYSEA CSVに実際に表示されたことを確認してから、AIチームがApp 674を更新する。
- App 674への一括更新前に:
  1. 対象レコードのJSONバックアップ
  2. 変更前後を示すドライラン一覧
  3. 浜田との確認
  4. 浜田GO後に更新
- SKYSEA CSVにありApp 674にないPCは、自動登録せず **台帳未登録PC**一覧へ出す。
- App 674のPC名重複、PC名完全不一致は自動解決・曖昧一致しない。
- 台帳未登録、重複、名称不一致の判断は浜田が行う。必要なPC端末名修正も浜田が行う。
- App 674のSKYSEA状態に **接続待ち / 再試行中 / 要確認**を追加する。
- 配信途中は実行ログを基に状態・確認日時・履歴を更新する。
- 最終「インストール済み」はSKYSEA CSV確認後のみ確定する。

### 11.11 App 674の権限

- 通常のApp 674一覧・業務機能は従来どおり。
- SKYSEA関連フィールドとSKYSEA進捗一覧だけを、kintoneログインコード **`admin` のみ閲覧・操作可**にする。
- 画面上の非表示だけで済ませず、フィールド権限を設定する。
- AIチームによるSKYSEA項目更新も`admin`権限で行い、更新者`admin`として監査履歴へ残す。

### 11.12 ログ・後片付け

- 共有サーバーのログフォルダーはインストーラー用フォルダーと分離する。
- ログ内容はPC名、実行日時、結果、終了コード等の必要最小限。利用者パスワード・認証情報は記録しない。
- PC名ごとのサブフォルダーに分離し、対象PCは自PCログのみ書き込み可能、閲覧は浜田の管理者アカウントに限定する。
- ログ保存期間は全台完了後 **3か月**。
- SKYSEA CSV確認後の後処理:
  1. 対象PCを専用ADグループから外す
  2. 配信用スケジュールタスクを削除する
  3. 再配信されないことを確認する
- 全台完了後、専用GPOを即時無効化する。
- 専用GPOと専用ADグループは完了後3か月で削除する。
