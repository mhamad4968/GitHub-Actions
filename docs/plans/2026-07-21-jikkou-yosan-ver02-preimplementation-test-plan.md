# 実行予算支援ツール Ver.02 — 実装前試験・7/23信頼性検証計画

**作成**: 2026-07-21（実装前成果物）
**状態**: FINAL TEST DESIGN — AIチーム再監査PASS／実装・アプリ作成・テスト実行は未許可
**対象仕様**: P-21〜P-44、V1〜V13、U1〜U30、Y1〜Y11
**公式期待値**: 7/23に依頼者が提供する正データ入力済みExcel（P-31/R-24）

## 1. 試験の目的

1. 実行予算の金額・丸め・集計に誤差や二重計上がないこと。
2. 3アプリ分割でも、利用者は①の1画面から安全に入力・閲覧できること。
3. 版管理で旧版へ誤入力できず、実績は版をまたいで1回だけ存在すること。
4. 同時操作・古い画面・重複作成でもデータが壊れないこと。
5. Excel原本の壊れた参照を再現せず、依頼者の正データExcelを期待値にすること。

## 3. 計算試験

### 3.1 請負（P-22）

| ケース | 入力 | 期待 |
|---|---|---|
| C-01 通常積 | 数量2×単価100 | 200 |
| C-02 小数積 | 数量1.5×単価101 | 内部151.5（ROUNDしない）。画面は152 |
| C-02b 複数小数行 | 内部100.4＋100.4 | ①内部200.8→表示201。表示行100＋100=200は①計算に使わない |
| C-02c 給与小数積 | 数量1.5×単価101 | 内部151.5、画面152。給与計は内部値合計 |
| C-03 数量空 | 数量空×単価100 | 金額空 |
| C-04 単価空 | 数量2×単価空 | 金額空 |
| C-05 代表案件① | 依頼者正Excelの請負明細 | 施工計・保安計・①が全一致 |

十進演算を使用し、JavaScript `Number`の二進誤差を計算根拠にしない。kintone数値フィールドには内部十進値を保存し、カスタムUIで0桁表示する。

### 3.2 内訳明細（P-22）

| ケース | 入力 | 期待 |
|---|---|---|
| C-10 通常 | 2×100 | 200 |
| C-11 .5未満 | 1.2×100.2=120.24 | 120 |
| C-12 .5 | 1×100.5 | 101（Excel ROUND同等） |
| C-13 負数 | -1×100.5 | Excel ROUND同等の負数結果 |
| C-14 ％行 | 単価10,000×数量1.25％ | 125 |
| C-15 空値 | 数量または単価が空 | 金額空 |

JavaScriptの`Math.round`だけでExcel `ROUND(...,0)`を代用しない。負数・浮動小数誤差を含めた専用円丸め関数をG1で固定する。

### 3.3 ブロック集計・総括投影（U25/P-21）

| ケース | 期待 |
|---|---|
| C-20 小計 | 円丸め済み明細合計＋手入力諸経費＋手入力保険料 |
| C-21 計 | 小計＋手入力法定福利費。計を再ROUNDしない |
| C-22 空フッタ | 空の手入力額は加算上0、表示は空可 |
| C-23 総括投影 | 同じ`stable_block_id`の総括原価行だけに「計」を反映 |
| C-24 二重参照防止 | 2ブロックが同じ合計を共有しない |
| C-25 並替 | 内訳№は詰め直すが`stable_block_id`と金額対応は不変 |
| C-26a 実績なし下書き削除 | ②ブロックと①投影行を物理削除。他ブロックは不変 |
| C-26b 実績あり削除操作 | 物理削除せず`retired`。①現行投影は予算0、③実績は保持 |
| C-27 混在単位 | 総括は単位`式`・数量1・単価=税抜計 |
| C-28 投影不一致 | ①キャッシュを故意に変更しても⑧⑨は②から正しく再計算。版確定は拒否し②から①を自動修復 |
| C-29 同期方向 | ①キャッシュ変更が②「計」へ逆流しない |

### 3.4 ①⑧⑨・率

- ①＝請負施工計＋請負保安計
- ⑧＝**②の`active`ブロック計**（施工＋保安）＋①給与手当計。`retired`・①投影キャッシュを計算入力にしない
- ⑨＝①−⑧
- 原価税込＝行単位`ROUND(税抜×(1+税率),0)`。税込合計は丸め済み行合計
- 対①率の保存値＝`ROUND(金額÷①×100,1)÷100`（比率）。UIは`0.0%`表示。①=0は0%
- 予実の消化率も同じ比率保存・小数1位%表示。現行予算=0は「—」
- 残予算＝現行予算−実績
- 今後必要額＝`max(0, 実績−最終予算額)`

境界試験: 税率0/8/10%、税込端数±0.5、①=0、現行予算=0、率の0.05%境界、負数を十進Excel互換ROUNDで確認。

## 6. 重複作成ダイアログ（P-29）

1. 同じ工事コード＋枝番、下書きなし: 「次の版を作成しますか？」
   - はい: 最新確定版を複製。新規画面入力値は使わない。
   - いいえ: 保存しない。
2. 同じ工事コード＋枝番、下書きあり: 「既存の下書きを開きますか？」
   - はい: 既存下書きへ遷移。
   - いいえ: 保存しない。
3. 2人が同時に初版作成: 片方だけ成功し、他方は一意制約エラーを説明表示。
4. 2人が同時に次版作成: 同じ`version_record_key`の片方だけ成功。

## 8. 7/23 Excel信頼性突合

### 8.1 受領時チェック

- ファイル名、受領日時、作成者、対象工事コード＋枝番を記録
- 原本SHA256を記録し、突合中に差し替わらないよう固定
- 「依頼者が検算済みの正データ」であることを口頭またはメールで確認
- 数式セルと保存値の両方を読める状態か確認

### 8.2 比較単位

1. 工事ヘッダ
2. 請負明細各行→施工計→保安計→①
3. 内訳各明細の丸め結果
4. 各ブロック小計・計
5. `stable_block_id`相当の工種ごとの総括原価行
6. 施工計・保安計・給与計→⑧→⑨
7. 月別消化→実績合計→残予算→消化率→最終予算→今後必要額

### 8.3 差分分類

| 分類 | 内容 | 処置 |
|---|---|---|
| A 実装バグ | 確定仕様とコードが違う | 実装修正・再試験 |
| B 仕様誤り | コードは仕様どおりだが依頼者期待と違う | 該当Rへ差し戻し、浜田決定 |
| C Excel破損 | `#REF!`・二重参照・不正セル | Excelは再現せず依頼者へ正値確認 |
| D 入力差 | 数量・単価・率・税率が違う | 入力を揃えて再比較 |
| E 表示差 | 保存値一致、丸め表示だけ違う | 表示仕様を確認 |

### 8.3b 初回から比較不能として固定する項目

- 破損原本の`#REF!`を含む⑧⑨・月別消化セル
- Excelの二重参照・無効`ARJ`参照
- Excel旧定義と意味が違う「今後必要額」「最終予算額」
- 不採用とした`1−率`・帯小計率
- R-11〜13により初回手入力とした諸経費・保険料・法定福利費の自動式
- 率は保存比率（例0.123）と画面百分率（12.3%）を分けて比較

比較不能項目を一致扱いにせず、依頼者判断・理由・次対応を記録する。

### 8.4 合格条件

- 比較可能な全金額で差額0円
- 例外は「比較不能理由・依頼者判断・次対応」を記録し、黙って合格にしない
- P-21/P-22/P-30は依頼者が「問題なし」または修正内容を明示
- 一致率だけで合格にせず、①⑧⑨と各ブロック計は全件確認

## 9. 非機能・安全試験

- App 735/736の設定・レコード・customize・revisionが不変
- ②③を直接開いた通常利用者が画面操作で正規保存経路を迂回できない（意図的REST直実行はP-35により初回対象外）
- ②③の直接編集画面からの保存をカスタマイズが拒否し、正規保存の`write_channel=app1_custom_ui`が記録される
- ②旧版は`parent_lock_snapshot=locked`のレコード権限により、直接REST更新も通常利用者権限では拒否される
- API失敗時に親だけ／子だけ保存された中間状態を検出し、再実行可能
- 数百件の②複製はP-34の1回の`bulkRequest`へ100件単位で格納。N=763で旧①1＋新①1＋新②8＋旧②ロック8＝18要求を確認
- N=900は20要求で許可、N=901は22要求（`2+2×ceil(901/100)`）になるためAPI送信前に中止
- 旧版更新には取得済み`revision`を指定し、他者更新後は全体をロールバック
- 個人情報・認証情報をログへ出さない
- 監査ログに工事ID、版ID、操作、成功/失敗、件数を残す
