## 3. レコード単位・主キー相当

- **1 レコード = カレンダー上の 1 日**（**記録日**は **必須**）。
- **運用既定（浜田決定）**: **毎日 1 行**を置く（旧・案②）。**問い合わせがなければ** 午前 **0**・午後 **0**（日合計は計算で **0**）。**問い合わせがあれば** 実件数を午前・午後に入力する。**土日祝も例外にせず、同じルール**（多くの土日祝は 0、発生時のみ実数）。
- 同一記録日の重複は **`customize/682/desktop.js` の保存直前（`create.submit` / `edit.submit`・モバイル同イベント）で REST により拒否**する（**2026-05-12 CEO 重要確認**）。**同時保存の競合**は kintone 標準に **暦日ユニークの DB 制約が無い限り**理論上残るため、必要なら **プラグイン／API 取込手順**で別途抑止する。

### 3.1 未入力と 0 件の取り違え（注意）

- **リスク**: 行はあるが **午前・午後が空欄**のままだと、「まだ入力していない」のか「0 件で確定」のかが一覧上わかりにくい場合がある（第2者メモ: 混同）。
- **対策（運用で明示）**: 例として **「翌営業日の開始時点で前日まで必ず 0 か実数を入れる」**、または一覧で **空欄ゼロ**を週次チェックする、などを実装フェーズで **手順 1 行**に落とす。

## 4. フィールド（MVP）

| フィールドコード（案） | 表示名 | 型 | 必須 | 備考 |
|------------------------|--------|-----|------|------|
| `record_date` | 記録日 | 日付 | はい | 集計・グラフの主軸。**対応日**として扱い、**新規作成時**に未入力なら **Asia/Tokyo の当日**を `desktop.js` で既定入力。**一覧・詳細の表示**および**新規・編集の補助行**は `desktop.js` で **`yyyy/mm/dd(曜)`**（例: `2026/05/08(金)`）に揃える。保存値の形式は **YYYY-MM-DD** のまま（表示のみ上書き／補助は別要素）。 |
| `am_count` | 午前件数 | 数値（整数） | はい | **対応内容の行数のみ**で自動（下記 §4.1）。**画面では編集不可（disabled）**。**無件は 0**。 |
| `pm_count` | 午後件数 | 数値（整数） | はい | **同上（午後の対応内容 → 午後件数）**。 |
| `day_total` | 日合計 | 計算 | （自動） | **`am_count + pm_count`**。 |
| `am_correspondence` | 午前の対応内容 | 文字列（複数行） | いいえ | **1 行 = 1 件**で箇条書き。**保存時**に **行数で `am_count` を上書き**（空なら **0**）（§4.1）。 |
| `pm_correspondence` | 午後の対応内容 | 文字列（複数行） | いいえ | **1 行 = 1 件**で箇条書き。**保存時**に **行数で `pm_count` を上書き**（空なら **0**）（§4.1）。 |

- **カテゴリ等**: 原則 **不要**。傾向分析で必要になれば **後から追加**（浜田合意）。
- **曜日**: 入力負荷を増やさない。**記録日から導出**できるなら計算／自動で可（任意・後追い可）。
- **祝日フラグ**: 任意。精度が必要になったら追加検討。

### 4.1 対応内容から件数を拾う（実装方針）

- **標準の計算フィールド**では「複数行テキストの行数」は扱えないため、**ブラウザ用 JavaScript**（`customize/682/desktop.js`）で **保存直前**（`create.submit` / `edit.submit`）に件数を埋める。
- **数え方**: 改行で分割し、**前後空白を除いて空でない行を 1 件**とみなす（`-` や `・` で始まらなくても 1 行 1 件でよい）。
- **件数フィールドは編集不可（2026-05-09 浜田決定）**: `am_count` / `pm_count` は **`app.record.create.show` / `edit.show`** で **`disabled = true`**。入力者は **数値を直接変更できない**（対応内容の箇条書きのみが件数の入力経路）。
- **空欄は 0 件**: 対応内容が **空白のみ**のときは、保存直前に **`am_count` または `pm_count` を `0`** にする（§3「無ければ 0」と整合）。
- **記録日＝対応日（2026-05-09 浜田決定）**: **新規作成**で `record_date` が未入力のとき、**Asia/Tokyo の当日**を `create.show` / `create.submit` で補完する。
- **注意**: 1 件の説明を **複数行に分ける**と件数が増える。長文は **1 行にまとめる**運用を推奨。

## 5. グラフ（月ベース）

- **暦月**で集計する（例: 4月 = **4/1〜4/30** を 1 本の月として棒グラフに反映）。
- **日次レコード**がソースのため、**日ベースで入力された結果**は、該当日が属する暦月の集計に **自動的に反映**される（kintone 標準集計の挙動に準拠）。
- **月次棒グラフの集計対象（浜田合意）**: **`日合計`（`day_total`）のみ**を使う。**午前・午後はグラフ集計に使わない**（二重計上防止・運用の単純化）。
- **注意**: 計算フィールドが未反映・未入力の状態では棒の値が **0 や期待とずれる**ことがある。公開前に **数式再計算・サンプル日で目視**する。

### 5.1 月次棒グラフ（kintone 標準 UI・CIO 手順メモ）

**REST 代替（2026-05-10）**: 管理画面と同等の設定を **`PUT /k/v1/preview/app/reports.json`** で投入し **`preview/app/deploy.json`** まで行う手順を **`npm run 682:graph-monthly`**（`scripts/user-support-682-ensure-monthly-bar-graph.mjs`）に実装。**種類は縦棒（API 上 `chartType: COLUMN`・`chartMode: NORMAL`）**。**フィルタ**は **Asia/Tokyo の「今月」を末尾**とし、**その月の 6 暦月前の 1 日〜今月末**（月次グループで最大 **7 本**の棒）を **`filterCond`** に静的保存する（**窓を更新するたびにスクリプトを再実行**する）。**自動**: GitHub Actions **`.github/workflows/682-graph-monthly-refresh.yml`** が **毎月 1 日（UTC cron）**に **`cio:preflight:682` → `682:graph-monthly:scheduled`** を実行し、**`filterCond` を作り直す**（**Repository secrets** のみ・`environment` なしで **承認ゲートに止まらない**。詳細は Runbook §1.0）。**既存グラフがあるアプリではマージ必須**（省略すると削除される API 仕様のため、スクリプトは GET 全件を再送する）。

**前提（§5 再掲）**: 集計系列は **`日合計`（`day_total`）のみ**。午前・午後のフィールドは **グラフ系列に追加しない**（二重計上防止）。

1. アプリ **682** を開く → **設定**タブ → **グラフ**。
2. **集計グラフ**を追加（または既存を編集）。
3. **種類**: **縦棒**（集計グラフ API では **`COLUMN`**＋**`NORMAL`**。横棒の **`BAR`** ではない）。
4. **集計の設定**: 集計対象フィールドに **`日合計`（`day_total`）** を選び、集計方法は **合計**（または「値の合計」に相当する既定）。
5. **グループ（横軸）**: **`記録日`（`record_date`）** を選び、**グルーピング**を **月ごと**（暦月）に設定する（UI 名は環境により「月単位」等）。
6. **フィルタ**（推奨）: **直近 7 暦月**（JST 今月を含み、先頭は今月の **6 暦月前**の月初）で **年間に近い横軸**を確保する。REST 手順では **`npm run 682:graph-monthly`** 実行時に上記範囲の **`filterCond`** を生成する。
7. **プレビュー**で、サンプル日を入れたレコードが **該当月の棒に反映**されることを確認する（§3 の「1 日 1 行・0 明示」運用と整合）。
8. **公開**前に、**計算フィールドの再計算**（一覧の再読込やレコード保存）で `day_total` が期待どおりかを確認する（§5「注意」）。

**DeepSeek 盲点突合（§50-3-8）**: (a) `day_total` はフォーム上 **計算（数値）** として定義済みであるため、通常はグラフで数値系列として扱われる（もし表示が常に 0 なら **フィールド型・グラフの集計対象取り違い**を疑う）。(b) SPEC 上、グラフは `day_total` のみであり **午前・午後を同時系列にしない**ことで、JS の件数上書きとの **二重計上は設計上回避**している。(c) 保存順は **クライアント `submit` で `am_count`/`pm_count` 更新 → サーバ側で `day_total` 再計算**のため、**同一レコード内で CALC と競合する二重上書き**にはならない（別レコードの集計はグラフ側の集約ルールに従う）。

**標準グラフの制約（2026-05-09 追補）**: kintone **標準の集計グラフ**は、**その月に 1 件もレコードが無いと横軸にその月が現れず、0 棒も出せない**（製品仕様）。**7 暦月すべてを 0 含めて見せる**補完は **[683 ダッシュ](https://jbis-kintone.cybozu.com/k/683/)**（`customize/683/desktop.js`・REST）を正とする（**2026-05-12 CEO 重要確認**）。**682** の **`customize/682/desktop.js`** では **`SHOW_ROLLING_7M_ON_APP682 === false`** とし、**一覧ヘッダ・レポート画面に REST の 7 暦月棒を出さない**（欠日・重複バナー等の §6.2.1 は従来どおり）。標準グラフ本体（`682_day_total_monthly`）の維持は従来どおり `682:graph-monthly`。**正本手順（682 側 REST 棒を戻す場合のみ）**: `SHOW_ROLLING_7M_ON_APP682` を **`true`** → **`npm run cio:preflight:682 -- --note "…"`** → **`npm run deploy:682`**（`BUILD` 更新を伴う）。

### 6.2 データ鮮度・欠日・重複（浜田合意・2026-05-09）

- **目的**: §3 の「**1 日 1 行**」運用が崩れているとき、**ダッシュボード上**で入力者に気づいてもらう（**外部 LLM 不要**・集計のみ）。
- **欠日（暦月ベース）**: 表示中の **対象月**（既定は **当月・`Asia/Tokyo` の暦**）について、**その月のうち「入力が求められる日」**の件数を **N**、そのうち **`record_date` のレコードがある日**を **M** とする。**M < N** なら警告文を出す。  
  - **当月の「求められる日」（2026-05-09 CEO／CIO 判断）**: **当月 1 日〜`Asia/Tokyo` における昨日**まで（**当日および未来の暦日は未入力扱いに含めない**）。例: 5 月 9 日 JST 時点では **5/1〜5/8** が母数（5/9 以降は警告の欠日に **含めない**）。**昨日が前月に落ちる**（例: 当月 1 日 JST）のときは、**当月については欠日母数 N=0**（欠日バナーは出さない）とする。  
  - **文言の例**: 「**〇 / 〇 日分が未入力です。入力をお願いします。**」（前半は **M / N** または **欠け日数（N−M）** を明示してよい。実装で統一する）。
  - **欠日列挙の表記（バナー・customize）**: **`yyyy/mm/dd(曜)`**（例: `2026/05/08(金)`）。`ja-JP` の短い曜日表記を用いてよい。**一覧・詳細・新規編集の補助行**の `record_date` 表示は **`customize/682/desktop.js`** で **`yyyy/mm/dd(曜)`** に揃える（§4 フィールド表・保存値は YYYY-MM-DD のまま）。
  - **土日祝**: SPEC §3 どおり **例外にしない**（**N は暦の全日数**）。祝日を自動除外する場合は **別途祝日マスタ**が要るため、**MVP では暦全日を母数とする**。
- **重複**: **同一 `record_date`（暦日一致）**のレコードが **2 件以上**あるとき、**「同一記録日の重複があります。一覧で修正してください。」**のような **警告 1 行以上**を出す（重複日は列挙してよいが **最大件数は実装で上限**可）。**新規・編集の保存**については **上記に加え**、**682 の `desktop.js` が同一暦日の別レコードを検出した場合は保存エラー**とする（§3・**2026-05-12**）。
- **実装メモ**: kintone 標準グラフだけでは不足するため、**Space 48 のポータル／`customize/682/desktop.js` 以外の埋め込み**等で **REST または一覧 API** により月内 `record_date` を取得し集計する想定（§9.1 **D** 以降で具体化）。

### 6.2.1 実装の優先順（CIO 判断・2026-05-09 CEO「CIO に進めてよい」）

- **MVP（先行）**: **アプリ 682 のレコード一覧**（`app.record.index.show`）の **ヘッダスペース**に、§6.2 の **欠日／重複／API 失敗**を **同一ロジック**で表示する（**外部 LLM なし**・`kintone.api` GET `/k/v1/records.json`）。
- **対象暦月の切替（JST）**: ヘッダに **前月／次月／今月に戻す** を置き、**欠日・重複の集計クエリは選択した暦月**で行う（**既定は JST の今月**）。選択状態は **`sessionStorage`** で保持する（プライベートモード等では保持できない場合あり・`try/catch` で握りつぶし）。**過去月**（例: 4 月にデータが入っている月）はそのまま **月全体を母数**に含めて欠日を数える（`analyzeMonthRecords` の **JST 昨日クリップ**が月末で止まる）。
- **Space 48 ポータル**: **同一集計ロジックの再利用**を前提に §9.1 **D** で配置（**初回は 682 上で運用検証**してからでもよい）。
- **500 件超**: 当月クエリは **offset ループ**で全件取得する（**1 暦月で 31 件を大幅に超える運用**は想定外だが、取得件数が `limit` に達したら **追加取得を続行**）。それでも欠落する場合は **「件数が多く集計できませんでした」系**のエラー表示にフォールバックする。
- **重複警告の対象月**: クエリは暦月フル範囲のままとし、**当月内で `record_date` が重複している日**は **未来日であっても**警告する（重複はデータ不整合のため）。
- **API 失敗**: ネットワーク等で取得できないときは **黄色系の 1 行**で知らせる（サイレント失敗禁止）。

- **外部の有償 LLM は使用しない（B 案）**（浜田決定・コスト不可）。ページ 2 の文面は **ルールベース**および **定型文の組み合わせ**のみで生成する。
- **各日のブロック構成**:
  1. **問い合わせ内容の要約**: `am_correspondence` / `pm_correspondence` から **機械的ルール**（先頭行の抜粋、非空行の列挙・重複抑止、件数帯に応じた定型句など）で **短文**を組み立てる。**完全な自然文要約は求めない**（期待値は **一覧レベル**）。
  2. **件数**: **`day_total` を正**とし、**「本日の件数は〇〇件であった。」**のように **1 行で明示**する。対応内容が空でも **`day_total` は表示**する（要約と **役割分離**）。
  3. **相対コメント（任意 1 行）**: 当月内で **他日より件数が多い日**であるときのみ、**追加の 1 行**でその旨を示す（例:「本日は同月内の他日と比べ件数が多めでした。」）。**§7.2 のガードをすべて満たす場合に限る**。
- **ダッシュボード上の AI**（§6・§9.1 **E**）とは **別経路**とする。§9.1 **E** で LLM を採用しても、**ページ 2 の生成に外部 LLM を用いない**（本節の B 案は変更しない）。

### 7.2 「件数が多め」の表示条件（ガード）

- **比較の母集団**: **同一暦月**内の **他レコード**（`record_date` が同一月かつ当日以外）の **`day_total`**。**記録日**は **`Asia/Tokyo`** の暦日として解釈する（§4.1 と整合）。
- **条件**:
  1. **データが薄い月は出さない**: 当該月において **`day_total` > 0** の日が **3 日未満**のときは、§7.1(3) の行を **印刷しない**（誤判定抑制）。
  2. **閾値**: 上記 (1) を満たし、かつ **当日の `day_total` が、その月の「他日」の `day_total` の中央値より大きい**ときに限り、§7.1(3) を **表示してよい**（中央値は **他日のみ**で算出する）。
