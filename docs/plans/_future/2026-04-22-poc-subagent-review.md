# 第 1 章 4 層ガードレール（L0-L3）の定義 ⭐ 本書の核

## 1.1 基本思想

サブエージェントに与える「自由」は、**フォルダ粒度** と **コマンド粒度** の **両方** で厳格に縛る。
**「読める範囲」「書ける範囲」「実行できる範囲」を独立に階層化** することで、1 つの権限が穴になっても他の層が止める **多重防衛** を実現する。

---

## 1.2 4 層の早見表

| 層 | 名称 | 一言で | 承認者 | 用途例 |
|---|---|---|---|---|
| **L0** | 完全自由 | 読み取り専用 | 不要 | ドキュメント調査 / ログ解析 / コード grep |
| **L1** | 安全圏書込 | 一時ファイル / 生成物 | 不要 | レポート出力 / snapshot 保存 / ログ記録 |
| **L2** | 要承認（本体コード）| プログラム本体・正本ドキュメント | **メイン AI レビュー必須** | `customize/` `scripts/` `kintone-apps.md` 等の編集 |
| **L3** | 絶対禁止（人間承認のみ）| 不可逆操作 | **浜田の明示承認のみ** | `rm -rf` / kintone bulk delete / `git push --force` |

---

## 1.3 L0（完全自由 / 読み取り専用）

| 観点 | 内容 |
|---|---|
| **権限** | 読み取りのみ（write / execute いずれも不可） |
| **対象範囲** | リポジトリ全体 + 公開 Web |
| **許可ツール** | `Read` / `Glob` / `Grep` / `WebFetch` / `WebSearch` / `Glob` / 各 MCP の read 系メソッド |
| **禁止ツール** | `Write` / `StrReplace` / `Shell`（読み取り Shell も含む / 実行は L1 以上で別途）|
| **承認フロー** | 不要（即実行）|
| **実装方法** | Cursor `Task` 呼出時に `readonly: true` を指定。Ask モードで起動 |
| **違反検知** | 不要（write/execute ツール自体が呼べない構造）|

**用途例**:
- 既存コードの調査（「`bulkRequest` を使ってる箇所を全部探して」）
- ログ解析（「直近 100 行の cron ログから失敗パターンを抽出して」）
- 仕様書の通読・要約（「`new-pc-ledger-spec.md` を読んで矛盾点を 3 点だけ挙げて」）

---

## 1.4 L1（安全圏書込 / 一時ファイル・生成物）

| 観点 | 内容 |
|---|---|
| **権限** | 限定フォルダ内に限り Write / StrReplace 可。**コード本体・正本ドキュメントは触れない** |
| **書込許可フォルダ（ホワイトリスト）** | `tmp/` / `logs/` / `data/snapshots/` / `data/skysea/` / `docs/extracts/` / `docs/reports/` / `docs/approved-changes/` / `/tmp/`（Linux 一時領域）|
| **書込禁止フォルダ** | 上記以外すべて（特に `customize/` `scripts/` `kintone-apps.md` `AGENTS.md` `chat-sessions/checkpoint-latest.md` `~/.cursor/` `.env*` 等）|
| **許可コマンド（Shell）** | `ls` / `cat`（実は Read 推奨）/ `wc` / `git log` / `git diff` / `git status` / `npm run` の **read 系のみ**（test / lint / outdated 等。deploy / push / publish は除外） |
| **禁止コマンド** | `rm` / `mv`（書込先以外への mv）/ `git commit` / `git push` / `npm publish` / 等 |
| **承認フロー** | 不要（即実行）|
| **実装方法** | Cursor `Task` 呼出時に **書込許可フォルダ一覧を prompt で明示** + Cursor Hook で `pre-write` パスバリデーション |
| **違反検知** | file-watcher が変更検知 / pre-write Hook がパス外の write をブロック |

**用途例**:
- 「レビュー結果を `logs/poc-review/2026-04-22.json` に出力して」
- 「kintone API で 627 全件取得して `data/snapshots/627-2026-04-22.json` に保存して」
- 「コード解析レポートを `docs/reports/2026-04-22-code-audit.md` に書いて」

---

## 1.5 L2（要承認 / プログラム本体・正本ドキュメント）

| 観点 | 内容 |
|---|---|
| **権限** | 本体コード・正本ドキュメントへの **編集提案** はできるが、**実書込は禁止**。サブは **diff を返すだけ** |
| **対象フォルダ・ファイル** | `customize/` / `scripts/` / `kintone-apps.md` / `AGENTS.md` / `WORKFLOW.md` / `CLAUDE.md` / `RULES-INDEX.md` / `chat-sessions/2026-XX-XX.md`（記録）/ `package.json` / `package-lock.json` / `.cursor/rules/`（リポ側）/ `.cursor/skills/` |
| **許可動作** | サブは「この path に対してこういう変更を提案します」と **diff のみ返す**。実 write は **メイン AI が責任を持って Apply** する |
| **承認フロー** | サブ diff 返却 → **メイン AI が §47/§48/§49 でレビュー** → メイン判断で Apply（または却下・修正）→ 重大変更は人間承認も挟む |
| **実装方法** | サブ起動時に `readonly: true` で起動 + 出力フォーマットに `proposed_diff` フィールドを必須化 |
| **違反検知** | サブが直接 write した場合は file-watcher が即検知 / git pre-commit hook で「サブ起動セッション内で L2 ファイル変更されたら警告」|
| **テストファイル特例** | `*.test.*` / `__tests__/` / `tests/` 配下は **L2 内でも特に厳格** = サブには **diff 提案すら原則不可**。テスト変更が必要なら**メイン AI が単独実装**（第 5 章で詳述）|

**用途例**:
- 「`customize/627/desktop.js` の `calcPcLinkCount` 関数を §15 完成度 4 要件でレビューして、改善 diff を提案して」
- 「`AGENTS.md` §41 の文言を§47/§48/§49 と整合する形で改善 diff を提案して」
- → 提案を受けたメインが「採用」「修正」「却下」を判断 → メインが Apply

## 1.6 L3（絶対禁止 / 浜田の明示承認のみ）

> **このカテゴリは、サブエージェントに権限を一切与えない。メイン AI も自律判断では実行しない。**
> **必ず浜田の明示的な「実行して」という発話を受けてから、メイン AI が実行する。**

### 1.6.1 物理削除系
- `rm -rf` / `rm -r` / `rmdir` / `find ... -delete`
- `git clean -fd` / `git clean -fdx`

### 1.6.2 GitHub / git 不可逆操作
- `git push --force` / `git push -f` / `git push --force-with-lease`
- `git reset --hard origin/<branch>`
- `git branch -D <branch>`（マージ前ブランチ削除）
- `git tag -d <tag>` + `git push origin :refs/tags/<tag>`（リモートタグ削除）

### 1.6.3 kintone 不可逆 API 操作 ⭐ 浜田指摘の「物理削除」だけでは抜ける危険箇所
- **bulk delete**: `/k/v1/records.json DELETE` / `/k/v1/records/cursor.json` の delete モード
- **bulk update で 50 件超の一括 PUT**（誤指定で全件上書きの実害が大きい）
- **アプリ削除**: `/k/v1/preview/app.json DELETE` / アプリ設定の破壊的変更
- **フィールド削除**（既存データ消失リスク）
- **アクセス権の全面再構築**（運用停止リスク）
- **ルックアップ元アプリの ID 変更**（参照破壊）

### 1.6.4 公開リリース・配信系
- `gh release create` / `gh release delete`
- `npm publish` / `npm unpublish`
- `gh api ... -X DELETE`（リポジトリ・Issue・PR の削除）
- メール一斉送信スクリプト

### 1.6.5 本番認証・秘密情報の操作
- `.env` / `.env.proxy` / `.env.*` の **write**（read もメインのみ）
- `~/.cursor/mcp.json` の **write**
- `~/.cursor/rules/*.mdc` の **write**（ホーム正本 = 関係性契約）
- API トークン rotation / OAuth 再認証

### 1.6.6 システム基盤の破壊
- `crontab -e`（cron 配信編集 / §22 同等の保護対象）
- `~/.cursor-emergency-backup/` の **削除・上書き**（最終防衛線）
- `chat-sessions/checkpoint-latest.md` の **削除**（編集はメイン AI のみ可 / L2 扱い）
- `scripts/file-watcher.mjs` の停止（防衛網の停止）

### 1.6.7 承認フロー
1. サブが「これをやりたい」と提案した場合 → **メイン AI が即拒否** + 「L3 操作なので浜田承認が必要」と返す
2. メイン AI が必要性を判断 → **浜田に 1 問で確認**（§41）
3. 浜田が「実行して」と明示 → **メイン AI が単独実行**（サブには絶対やらせない）
4. 実行前に **rollback プラン** を提示 + 実行後に **証拠ログ** を残す

### 1.6.8 実装方法
- Cursor `Shell` Hook で **正規表現マッチ** → L3 該当コマンドは **無条件で実行拒否**
- サブエージェントには **kintone API トークンの DELETE 権限を最初から与えない**（read-only token を分離）
- `.env.subagent`（write 禁止 token のみ）と `.env`（フルアクセス / メイン専用）を分離

## 1.7 階層を貫く 3 つの絶対原則

| # | 原則 | 内容 |
|---|---|---|
| 1 | **層の格上げ禁止** | サブエージェントが「これは L1 で扱える」と自己判断で層を下げてはいけない。判断はメイン AI のみ |
| 2 | **権限の最小化** | 各タスクで必要最小の層だけ与える。「念のため L2 で起動」は禁止 |
| 3 | **証拠の二重化** | L2 以上の操作は **メイン AI レビュー** + **file-watcher / git hook** の 2 系統で監視 |

## 1.8 既存防衛網との連携

本ガードレールは、**既存の継続性基盤を補強する形で組み込む**（既存資産は一切破壊しない）。

| 既存の防衛 | 本 PoC との関係 |
|---|---|
| `scripts/file-watcher.mjs`（PID 41917 常駐）| L1/L2/L3 違反で発生する write を即検知。本 PoC で書き換え不要 |
| `scripts/wipe-guard.mjs`（15 分 cron）| 0 byte 化検知。サブの暴走時の最終防衛線 |
| `~/.cursor-emergency-backup/`（4 時間 cron）| L3 違反で消えても 4 時間以内なら復元可能 |
| `scripts/watcher-watchdog.sh`（5 分 cron）| file-watcher 自体の死活監視 |
| **TSB-006 ガード（1 ターン 10 ファイル超で分割）** | **本 PoC で再定義必須**。サブが並列で書く場合、**メイン視点での総ファイル数カウント**に書き直す（既存ロジックを 4/22 中に修正候補化）|
