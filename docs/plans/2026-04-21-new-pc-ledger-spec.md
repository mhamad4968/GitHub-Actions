#### 4.1a 個人 × 保管（2026-04-30 浜田 GO）

- **`account_type`=個人**のまま **`pc_status`=保管** とするレコードは、**NAS/その他と同様にアカウント運用の対象外**とする（保管中の端末で **Windows/M365/595 メール等を台帳に載せない**方針）。
- **B-1 移行 CSV**: 当該行は **旧 627 と突合・マージしない**（JOIN 対象は **`pc_status`≠保管**の個人のみ）。アカウント系列は **空欄**でよい。
- **必須項目の緩和**: 上表の「個人 → `user_name` 必須」は、**`pc_status`=保管の個人**に限り **適用しない**（空のまま import 可）。**674 のフォームで `user_name` が必須のままだと CSV 取込が失敗する**ため、**取込前に当該フィールドの必須を外すか**、**移行専用に空でも通る検証**を kintone 側で調整する（実施は Tier B・浜田 GO のうえで CIO が実行）。
- **UI**: §4.5 のとおり **アカウント情報セクションは非表示**（個人用自動生成ボタンも出さない・§4.4）。

- **共有 PC（種別=共有）**: **Windows（新共有WindowsID採番マスタ）と M365（M365管理マスタ）の両方**を「共有用 自動生成」でフォームに表示（L1・§4.4）。
- **JR 端末（種別=JR）**: **M365（管理マスタ）のみ**が自動割当の対象。**`pc_name`（PC名）も §4.3.1 のとおり常に手入力**（個人・共有の JBIS / S-JBIS 系の **`pc_serial_no` 採番ルートの対象外**。自動生成ボタンでも **PC名は変更しない**）。**Windows 系（`logon_name` / `logon_pw` / `windows_name`）はすべて手入力**（AD 不参加・§4.3.2）。**自動生成ボタンでも JR の Windows 系は自動表示・自動埋めしない**（§4.4）。**既存も含め手入力値を正**とする。サイボウズ・ガリバーは **社内アカウントなし**（§4.2.2 どおり `gb_*` / `sb_*` は不要）。M365 をフォームに出す操作は §4.4（共有と **同一系のボタン**・表示条件に JR を含む。**674 実装**: JR のときボタン表記は **M365 反映**に寄せ、共有の「共有用」と混同しない）。

### 4.3 採番ロジック詳細

#### 4.3.1 PC 名（種別別自動採番）
- 個人: `JBIS` + 4 桁ゼロ埋め(pc_serial_no) + `-` + YYYYMM
- 共有: `S-JBIS` + 4 桁ゼロ埋め(pc_serial_no) + `-` + YYYYMM
- JR端末: **手入力**（既存命名のまま）
- 連番ソース: **新アプリ内で MAX(pc_serial_no) + 1**（マスタ依存なし）
- 既存移行 PC は `pc_serial_no = 0` で取込（新規発番分から 1, 2, 3...）
- **既存PC・従来名（浜田合意 2026-04-28）**: 個人・共有でも **`pc_name` は手入力した表記をそのまま保存してよい**（上記 `JBIS` / `S-JBIS` 形式に**合わせる義務はない**）。594 等の旧台帳名・現場で使っている名称を登録する。**自動採番は任意**（§4.4 の「手入力済値は保護＝マージ」に従い、ボタンで上書きしない運用とする）。`pc_serial_no` は **移行 `0`** のまま、または **手入力 `pc_name` の 4 桁と数値が一致しない**場合がありうる（カウンタは**新規自動採番用**と位置づけ、既存名登録と独立）。

#### 4.3.2 WindowsID（v2.1 改訂 / 新採番マスタ参照 + 厳格ルール）

**新規発番ルート**（新・PC台帳ver.1 の「自動生成」ボタン経由）:
- 個人: `^jbm\d{4}$` 厳格（4 桁ゼロ埋め）→ **新個人WindowsID採番マスタ**から払い出し
  - 採番開始: `jbm0001`
- 共有: `^sjbm\d{4}$` 厳格（4 桁ゼロ埋め）→ **新共有WindowsID採番マスタ**から払い出し
  - 採番開始: `sjbm0001`
- JR端末: **手入力**（AD 不参加のため自動採番しない）

**既存移行ルート**（CSV インポート経由 / v2.1 追加）:
- 既存 PC の AD ログオン名は `jbm00009` 等の **5 桁** が現実に存在 → 変更不可（OS ログオン名そのもの）
- 移行 CSV では **既存 AD 名をそのまま** logon_name に登録
- バリデーションは **緩和系統** を使用（`^jbm\d{4,6}$` 等で 5 桁許容）

**バリデーション 2 系統**（v2.1 追加 / 詳細は §4.7）:
| ルート | バリデーション | 対象 |
|---|---|---|
| 新規発番 | 厳格 (`^jbm\d{4}$` / `^sjbm\d{4}$`) | アプリ内ボタン経由 |
| 既存移行 | 緩い (`^jbm\d{4,6}$` / `^sjbm\d{4,6}$`) | CSV インポート経由 |

#### 4.3.3 M365 ID（v2.1 詳細化 / 共有 sjm-XXX 命名規則 + 5 台節約ロジック）

- 個人: `<mail_acct>@kensetsutoso01.onmicrosoft.com` （ドメインは環境設定マスタから取得）
- 共有/JR: **M365管理マスタから自動取得**（status=利用可 AND usage_count<5 の最古を取得）

**共有 M365 ID の命名規則**（v2.1 追加 / 浜田 4/22 確定）:
- フォーマット: `sjm-NNN@kensetsutoso01.onmicrosoft.com`（`NNN` = 3 桁ゼロ埋め連番）
- 採番開始: `sjm-001`
- M365管理マスタの `m365_id` フィールドにこの値で初期データ登録

**5 台節約ロジック**（v2.1 追加 / 浜田 4/22 確定 X 案）:
- 1 つの sjm-XXX は **最大 5 PC まで紐付け可**
- 6 PC 目を割り当てようとしたら、自動で **次の sjm（sjm-002 等）に切替**
- 例: 共有 PC 35 件なら `sjm-001`(5 PC) + `sjm-002`(5 PC) + `sjm-003`(5 PC) + ... + `sjm-007`(5 PC) = 7 個の sjm で 35 PC をカバー
- **M365管理マスタの初期データ**: B-2（共有 35 件）登録前に AI が `sjm-001` 〜 `sjm-007` を仮投入（35÷5=7、切上げで余裕）→ 詳細は §5.7

**Microsoft ライセンス・ポリシー（浜田確認 2026-04-28）**:
- **同一 M365 アカウントに紐づけてよい PC は最大 5 台まで**（`M365_LICENSE_LIMIT`＝§6.3）。**6 台目以降は Microsoft のアカウント／ライセンスポリシーに違反しうるため厳禁**—台帳・マスタ・割当ロジックで **厳重に注意**する。`usage_count` は **5 を超えない**運用を絶対条件とし、到達時は §4.6.4 の警告・満杯切替を必ず回す。
- **個人**: **1 社員 1 アカウント**かつ **社内規程で PC 所持は最大 2 台**（浜田 2026-04-28）。個人の M365 は **メール連動の別経路**（§4.3.3 個人行）であり、**同一 sjm 等の 5 台上限問題に通常は引っかからない**。**上記の厳重注意は共有・JR の M365管理マスタ割当が主対象**。

#### 4.3.4 競合対策
- 同時実行衝突対策: **楽観ロック (revision) + 自動リトライ最大 3 回**

## §5. M365管理マスタ — 詳細仕様

### 5.1 用途
- 共有/JR 用 M365 ID の **5 台ライセンス厳守管理**
- 払い出し・解放を新・PC台帳ver.1 から自動制御
- 個人 M365 ID は管理対象外（別ロジックで自動生成）

### 5.2 フィールド設計（10 個）

| code | type | 内容 |
|---|---|---|
| `m365_id` | SINGLE_LINE_TEXT (UNIQUE) | M365 ID（共有/JR 割当は **`sjm-NNN@…onmicrosoft.com`** 形式・§4.3.3。個人は本マスタ非対象）|
| `m365_pw` | SINGLE_LINE_TEXT | `kent2511K#`（環境設定マスタから取得）|
| `account_type` | DROP_DOWN | 種別（共有 / 個人）|
| `status` | DROP_DOWN | 利用可 / 満杯（5/5）/ 廃止 |
| `serial_no` | NUMBER | 連番（§5.3 の `ORDER BY serial_no` 用。例: `1` ↔ `sjm-001`）|
| `usage_count` | NUMBER (0-5) | 使用ライセンス数（自動更新）|
| `linked_pcs` | MULTI_LINE_TEXT | 使用中 PC 名一覧（カンマ区切り）|
| `created_at` | DATETIME | 作成日時 |
| `disabled_at` | DATETIME | 廃止日時 |
| `note` | MULTI_LINE_TEXT | 備考 |

### 5.3 自動割当ロジック

```javascript
1. 新・PC台帳ver.1 で **共有**なら「共有用 自動生成」／**JR**なら「M365 を自動反映（JR）」を押下（種別=共有 **または** JR端末。JR のときは **M365 系のみ**マスタ連携・**PC名は手入力のまま**・§4.1）
2. M365管理マスタを query:
   query: status = "利用可" AND usage_count < 5 ORDER BY serial_no ASC LIMIT 1
3. 該当 0 件（L2 反映 / v1.1 仕様変更）:
   - **自動で次連番を作らない・処理を中断**
   - alert「⚠ M365 アカウント空きなし。① Microsoft 管理画面で作成 ② マスタへ手動追加 → 再実行」
   - **PC 側の自動生成処理を中止** (フィールドへの値書込なし・保存もしない)
4. 該当 1 件取得 → **PC レコードのフィールドへ値表示**（保存ボタンまでは kintone 書込しない / L1 反映）
5. M365管理マスタ側:
   - usage_count を +1
   - linked_pcs に PC 名を追記
   - usage_count = 5 になったら status を「満杯」に自動切替
6. PC レコード保存
```

### 5.4 解放ロジック（PC 廃棄/削除時）

```javascript
1. PC ステータスを「廃棄」に変更 or レコード削除
2. 紐付き m365_id を取得
3. M365管理マスタの該当レコード:
   - usage_count を -1
   - linked_pcs から該当 PC 名を削除
   - status「満杯」 → 「利用可」自動戻し
```

### 5.5 整合性保証（TSB-008 教訓）
- `usage_count` は **CALC ではなく NUMBER + JS 自動更新**（CALC SUM の罠回避）
- **月次リコンサイル スクリプト**: 全 M365 ID について新・PC台帳ver.1 で実際に何台使われてるか再計算 → ズレ修正
- **監査ログ**: 割当・解放を `logs/m365-allocation.log` に記録

### 5.6 ビュー
- 標準: 全件・serial_no 昇順
- ⚠ 満杯一覧: filterCond=`status = "満杯"`
- 📊 使用率順: ORDER BY usage_count DESC

## §9. スケジュール（2026-04-22 19:30 改訂 v2 / 「急がず失敗回避」方針 + 1 日後ろ倒し）

### §9.0 スケジュールを正とする（浜田・AI 共通前提）

- **本節の表**は、新・PC台帳ver.1 プロジェクトの **稼働カレンダー上の単一正本** とする。浜田側が「スケジュール通り」で動く前提と同じく、**AI も着手順・報告の軸をこの表に合わせる**（手順書・チャットの都合だけで黙示のずらしをしない）。
- **前倒し禁止（浜田確定）**: **表の日付より前に**、当該行の成果物を **完了扱い**としたり、**本番系（674 への import 等）に投入**したりしない。余裕があるときは **同一期日内の品質・検証・下書き**に回す。**日程を繰り上げる**必要があるときだけ **表を改訂**し **§13** に記録する（**無記録の前倒し実施は禁止**）。
- **日付の置き方**: 表に載る「いつ・何をするか」は **浜田 × AI の相談で決めてから**載せる前提とする（一方だけの押し付け日付にしない）。
- **既定（デフォルト）**: 各行は **その日付までに完了**を目標とする。
- **例外（トラブル・依存先の遅れ等）**: 当日完了が不合理になるときは、その場で **浜田 × AI が再スケジュールを再検討してよい**。決まった内容は **§9 の表の更新**、または **§12 に原因・新期限・拾い直しを先に書き**後続で §9 を直す、のいずれかとし、**§13 改訂履歴に 1 行以上残す**（チャットだけで終わらせない）。
- **実績が表の日付行から遅延する場合**（上記の例外以外の事後整理も含む）は、**浜田判断のうえ (1) 本表の日付・作業文言を改訂する**か **(2) 表は据え置きでリカバリ作業を §12 等に明示**のいずれかとし、**§13 改訂履歴に 1 行以上残す**（口頭・チャットのみの合意にしない）。**日程を事実上繰り上げた**（表より前に当該成果を完了・本番投入した）場合も **同様に §13 必須**だが、**§9.0 の前倒し禁止**に反する無記録の繰り上げは認めない（繰り上げるなら **先に表を改訂**してから実施する）。
- 各行の「完了」の定義は、その行に書いた **作業列の成果物**に従う。曖昧になったら **§10 のチェックリスト**または **§12** で分解してから表に戻す。

### §9.0a 浜田単独では決められないとき（どう判断するか）

**AI が決め替えてよいことはない**（日付・仕様・社内合意の代理決裁はしない）。浜田が一人で裁けないときは、次の順で **種類を一つに決めてから**動く。

1. **§9 の日付を動かす問題か？**  
   - **Yes** → 部署ルールに従い **決裁権を持つ者**に持ち上げる。合意が返ったら **§9 の表を改訂**し **§13 に 1 行**（誰の合意か・旧行→新行）。AIは表の差分文案の下書きまで。
