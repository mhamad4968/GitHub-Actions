#### 4.1a 個人 × 保管（2026-04-30 浜田 GO）

- **`account_type`=個人**のまま **`pc_status`=保管** とするレコードは、**NAS/その他と同様にアカウント運用の対象外**とする（保管中の端末で **Windows/M365/595 メール等を台帳に載せない**方針）。
- **B-1 移行 CSV**: 当該行は **旧 627 と突合・マージしない**（JOIN 対象は **`pc_status`≠保管**の個人のみ）。アカウント系列は **空欄**でよい。
- **必須項目の緩和**: 上表の「個人 → `user_name` 必須」は、**`pc_status`=保管の個人**に限り **適用しない**（空のまま import 可）。**674 のフォームで `user_name` が必須のままだと CSV 取込が失敗する**ため、**取込前に当該フィールドの必須を外すか**、**移行専用に空でも通る検証**を kintone 側で調整する（実施は Tier B・浜田 GO のうえで CIO が実行）。
- **UI**: §4.5 のとおり **アカウント情報セクションは非表示**（個人用自動生成ボタンも出さない・§4.4）。

- **共有 PC（種別=共有）**: **Windows（新共有WindowsID採番マスタ）と M365（M365管理マスタ）の両方**を「共有用 自動生成」でフォームに表示（L1・§4.4）。
- **JR 端末（種別=JR）**: **M365（管理マスタ）のみ**が自動割当の対象。**`pc_name`（PC名）も §4.3.1 のとおり常に手入力**（個人・共有の JBIS / S-JBIS 系の **`pc_serial_no` 採番ルートの対象外**。自動生成ボタンでも **PC名は変更しない**）。**Windows 系（`logon_name` / `logon_pw` / `windows_name`）はすべて手入力**（AD 不参加・§4.3.2）。**自動生成ボタンでも JR の Windows 系は自動表示・自動埋めしない**（§4.4）。**既存も含め手入力値を正**とする。サイボウズ・ガリバーは **社内アカウントなし**（§4.2.2 どおり `gb_*` / `sb_*` は不要）。M365 をフォームに出す操作は §4.4（共有と **同一系のボタン**・表示条件に JR を含む。**674 実装**: JR のときボタン表記は **M365 反映**に寄せ、共有の「共有用」と混同しない）。

### 4.3 採番ロジック詳細

#### 4.3.1 PC 名（種別別自動採番）

- 個人: `JBIS` + 連番（1〜9999 は 4 桁ゼロ埋め。**10000 以上は桁そのまま**）+ `-` + YYYYMM
- 共有: `S-JBIS` + 同上連番形式 + `-` + YYYYMM
- JR端末: **手入力**（既存命名のまま。自動採番ルートの対象外）
- **連番ソース（2026-08-06 浜田 GO・実装済）**:
  - **空き番（歯抜け）は使わない**
  - **抽出**: いずれも **同一フィールド `pc_name`** から正規表現で連番を読む（個人=`JBIS`+数字、共有=`S-JBIS`+数字）。形式に合わない従来名は max 走査から **除外**（手入力のまま保存可・§下段）
  - **個人**: 廃棄・取消以外・**全 account_type** の `pc_name` から読んだ **JBIS 連番の max + 1**（**S-JBIS・番兵 9999 は除外**）。共有／他種別行が JBIS 名を再利用したときの **衝突回避**のため、個人-only 走査はしない。あわせて環境設定（670）**`PC_SERIAL_MIN_PERSONAL_JBIS`**（未設定時 **67**）未満にしない → 次番 = `max(max+1, 下限)`。**個人は `pc_serial_no` の最大を採番ソースに使わない**（複写・既定値の大きな数値で飛び番しないため）。採番結果はフォームの `pc_serial_no` へ **同期表示**するだけ
  - **共有**: 廃棄・取消以外・種別=共有の `pc_name` から読んだ **S-JBIS 連番の max** と、同条件の **`pc_serial_no>0` の最大**の **いずれか大きい方 + 1**（個人 JBIS は含めない）。個人との非対称は意図的
  - 番兵 **`JBIS9999` / `S-JBIS9999`**（プレースホルダ）は max に **含めない**
  - **一覧「次採番」バナー**と **個人／共有の自動生成**は **同一式**（表示と採番の食い違い禁止）
  - **`pc_name` が空の行のみ**自動で PC 名を埋める。**登録済み JBIS/S-JBIS 名は変更しない**
- 既存移行 PC は `pc_serial_no = 0` で取込してよい（カウンタは新規自動採番用）
- **既存PC・従来名（浜田合意 2026-04-28）**: 個人・共有でも **`pc_name` は手入力した表記をそのまま保存してよい**（上記 `JBIS` / `S-JBIS` 形式に**合わせる義務はない**）。594 等の旧台帳名・現場で使っている名称を登録する。**自動採番は任意**（§4.4 の「手入力済値は保護＝マージ」に従い、ボタンで上書きしない運用とする）。`pc_serial_no` は **移行 `0`** のまま、または **手入力 `pc_name` の連番と数値が一致しない**場合がありうる（カウンタは**新規自動採番用**と位置づけ、既存名登録と独立）。
- **個人→共有等で JBIS 名維持（浜田 GO 2026-08-07）**: 種別を個人から共有・JR 等へ変更する際、**現場ラベルとして個人 JBIS 形式（`JBIS…`・`S-JBIS` で始まらない）の `pc_name` を維持してよい**。個人 JBIS の次採番は **全 account_type** 走査で衝突回避済み（上段「個人」連番ソース参照）。
- **保存時ガード（674 customize・2026-08-07）**: **`account_type`≠個人** かつ **`pc_name` が個人 JBIS 形式**（`JBIS`+数字、`S-JBIS` は対象外）のとき、保存前に **確認ダイアログ**（日本語）— 共有等なのに個人 JBIS 名のまま／採番衝突回避済／備考に記録する旨。**キャンセル**で保存中止。**OK** で **`note`（備考）** に定型1行 `[運用] 共有等だがPC名が個人JBIS形式（現場ラベル維持・採番は衝突回避）` を追記（NFKC＋空白正規化で **重複防止**）。必須項目エラー等のハードチェック通過後に実行。
- **個人 PC 名の重複（674 customize・2026-08-07 浜田 GO）**: **種別=個人**かつ **廃棄・取消以外**の他レコードと **`pc_name` が全く同一**（trim 後・大文字小文字無視）のとき **保存不可（ハードブロック）**。JBIS コアのみ同じで月違い（例 `JBIS0016-202401` vs `JBIS0016-202402`）は **可**。詳細・編集では赤バナー（全く同じPC名が他レコードにあります／登録不可）。旧 **JBIS+4桁コア重複の室長確認（ソフト警告）** は廃止。

  - **クリア**: カスタム検索の **「条件クリア」**および実効条件クリア時はチェックを OFF にし、`npl674note` を search/hash から除去する。既存の `query` / `npl674kw` / `npl674sort` / 標準 `q` 同期と共存する。

#### 4.10.1 個人 PC = 1 ユーザー最大 2 台

- 古い PC = 自動で「廃棄」へ

- M365管理マスタの `usage_count` は変動なし、`linked_pcs` の PC 名のみ更新

#### 4.10.4 PC 廃棄時の M365 解放

- **595 未登録の氏名**: 転用チェック（`npl_transfer_manual`）が **ON** の保存では、在籍氏名と一致しない場合 **`該当なし` 系メッセージで保存不可**（個人・非保管・595 照合）。
- **廃棄の意味**: 選んだ **別の個人 PC レコード**を **`pc_status`＝廃棄**にし、**595 の PC 台帳リンクを解除**（既存 `runTransferDisposePut674` と同趣旨）。

- **転記フィールド**: `npl_disposed_pc_copy`（単一行）に **廃棄した旧 PC の `pc_name` を自動転記**（例: `<旧PC名>` のみ。**`pc_name` が空のときのみ** `674#<旧$id>` にフォールバック）。一覧の **キーワード検索（部分一致・トークン AND）**の対象に含める（`npm run pc-ledger:674:add-npl-disposed-pc-field-preview` でフィールド追加後に有効）。
- **`npl_disposed_pc_copy` の正本優先（2026-05-11 CEO 合意）**: **① 手入力が空でないときは手入力を正**とし、転用廃棄ウィザードによる **自動転記は行わない**（674 customize: `updateOperatorNplDisposedPcCopy674`）。**② 空欄のとき**、ウィザード完了時に上記例形式で **自動転記**する。**③** 同一利用者名の **廃棄候補となる個人PCが台帳上に無い**場合、自動転記の対象が無いため **空欄のままでよい**（運用上、台帳外の事情がある場合は手入力で補う）。
- **保存のみでは `npl_disposed_pc_copy` は埋まらない（2026-05-11 追補）**: 「転用」ON で **保存**しただけでは **当欄は自動入力されない**（ウィザード完了または手入力）。674 customize は **保存成功時**に **同一レコード `$id`・同一ブラウザ `sessionStorage` で 1 回限り**の `window.alert` で **「転用: 元PCを廃棄…」**への誘導を出す。
- **本番反映順（浜田 CEO GO・2026-05-11）**: **`npm run pc-ledger:674:add-npl-disposed-pc-field-preview` を成功させてから** `npm run cio:preflight:674` → **`npm run deploy:674`**。フィールド無しで customize のみ先に載せると **一覧検索 REST が失敗し得る**（`customize/new-pc-ledger-v1/desktop.js` 先頭コメント・`kintone-apps.md` 674 行と同旨）。**preview が失敗したターンでは deploy:674 に進まない**。
- **保存順序（将来の保存連動を含む正）**: **先にカレント（転用先）保存成功 → 旧レコード廃棄 PUT**。現行ウィザードは **即時 PUT 連鎖**だが、第二段失敗時は **画面アラート＋手修正**を出す。
- **転用チェックを外す操作**: **確認ダイアログ**（本当に外すか／キャンセルでチェック維持）。
- **PC 買替との併存**: 転用後の端末が **故障・老朽化で PC 買替**に進むケースは業務上あり得る。転用チェックの有無と **PC 買替**の意味が混線しないよう **文言・確認**で補う（ロールアウト §4 保留と併記可）。

### 5.3 自動割当ロジック

```javascript
1. 新・PC台帳ver.1 で **共有**なら「共有用 自動生成」／**JR**なら「M365 を自動反映（JR）」を押下（種別=共有 **または** JR端末。JR のときは **M365 系のみ**マスタ連携・**PC名は手入力のまま**・§4.1）
2. M365管理マスタを query:
   query: status = "利用可" AND usage_count < 5 ORDER BY serial_no ASC LIMIT 1
3. 該当 0 件（L2 反映 / v1.1 仕様変更）:
   - **自動で次連番を作らない・処理を中断**
   - alert「⚠ M365 アカウント空きなし。① Microsoft 管理画面で作成 ② マスタへ手動追加 → 再実行」
   - **PC 側の自動生成処理を中止** (フィールドへの値書込なし・保存もしない)
4. 該当 1 件取得 → **PC レコードのフィールドへ値表示**（保存ボタンまでは kintone 書込しない / L1 反映）
5. M365管理マスタ側:
   - usage_count を +1
   - linked_pcs に PC 名を追記
   - usage_count = 5 になったら status を「満杯」に自動切替
6. PC レコード保存
```

### 5.4 解放ロジック（PC 廃棄/削除時）

```javascript
1. PC ステータスを「廃棄」に変更して保存（**物理削除は §4.10.7 で禁止**）
2. 紐付き m365_id を取得
3. M365管理マスタの該当レコード:
   - usage_count を -1
   - linked_pcs から該当 PC 名を削除
   - status「満杯」 → 「利用可」自動戻し
```

**推奨運用（B-1）**

1. **事前に一度だけ**、浜田が **マッピング表のドラフト**（どの旧列→674 のどれ、A〜E、G1 の location は C で載せるか空か等）に **GO または差し戻し**を出す。ここで方針が決まれば、**同種のギャップは AI が繰り返し判断してよい**。  
2. **取込 CSV の生成・整形・ドライラン**は **AI が主**（手直し含む）。**例外一覧（D 候補・要判断フラグ付き）**を必ず添える。  
3. 浜田は **「サマリ＋例外一覧」単位**で確認する（**全行を 1 件ずつ聞かない**）。例外が **閾値以上**（例: 10 件超、または「要判断」が 1 件でも危ないもの）なら、その塊だけ **浜田が決めてから**再生成。  
4. **マッピング表に無い新パターン**が出たら、AIは **勝手に仕様を広げず**、**例外一覧に1行追加して止める** → 浜田が **1 回の返答**でルールを足す（§13 記録）。

**一文まとめ**: 定型は **AI が表に従って手直し**、**方針と例外塊だけ浜田**。272 行を毎回 1 件確認は **デフォルトにしない**。

**浜田運用の簡略版（これでよい）**: **例外が出たらその都度浜田に確認する**。AI は **判断が割れそうなときは進めず止めて聞く**（例外一覧に載せてからでもよい）。事前の **マッピング表 GO**（上記「推奨運用」1.）は、**最初の方針固定**のために残す。

**端末のキーについて**: kintone 上のシステム主キーはレコードの `$id` だが、**PC 台帳アプリ上で「1 台」を指す業務キーは `pc_name`**（必須・運用・検索の軸）。旧 594 との突合・追跡は **627 の `pc_594_record_id`** や **`extra_info_2` の `[594:record_id]`**、必要に応じて **`mail`** で行い、**人が見る単位・重複検出の第一キーは `pc_name`** と捉える（§4.2.1a・§4.3.1 と整合）。
