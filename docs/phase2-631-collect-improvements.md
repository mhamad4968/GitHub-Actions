# フェーズ2（案）— アプリ 631 採用メタデータ・上限例外・品質フラグ

**実装は未着手**の設計メモ。実装時は [`AGENTS.md`](../AGENTS.md) の **収集ガードレール（重大度例外枠）** を必ず守ること。

---

## 1. 目的

- **説明責任**: なぜその記事が採用されたかを kintone 上で追えるようにする。
- **品質**: Gemini 失敗・材料薄いレコードを一覧で切り出す。
- **重大インシデント**: 通常の日次上限を超えても限定的に追加できるようにするが、**API・通知のパンクを防ぐ上限**をコードと憲法に固定する。

---

## 2. フィールド設計（内部／表示の分離）

| 区分 | 例（フィールドコード案） | 型 | 用途 |
|------|---------------------------|-----|------|
| 表示・業務 | `match_keywords_display` または一覧用の簡易タグ | 複数行 or チェックボックス | 運用者が一覧で見る用（長い JSON は載せない） |
| 内部 | `internal_match_meta_json` | 複数行テキスト | マッチキーワード・スコア等の **JSON 全文**（監査・デバッグ） |
| 内部 | `internal_source` | ドロップダウン or 1行 | `rss` / `nvd` 等 |
| 内部 | `internal_gemini_mark` | 1行 | `Y` / `I` / `N`（既存ログと一致） |
| 表示 | `needs_review` | チェックボックス | 要レビュー（複合条件で自動セット） |
| 内部 | `internal_severity_tier` | 1行 | `normal` / `exception` 等（例外枠消費の追跡） |

**注意**: 「内部」フィールドは **アプリのアクセス権・一覧レイアウト**で一般ユーザーから隠す。JSON は **個人情報や URL の羅列**になりうるため、権限設計が必須。

---

## 3. `collect.ts` / `collect-enrich.ts` の変更イメージ

1. キーワードマッチ時に **マッチした語のリスト**を構造化（正規表現・部分一致の整理）。
2. `enrichOneNewsForKintone` の戻り値を拡張し、post 直前に `record` にメタフィールドをマージ。
3. **品質フラグ** `needs_review`: 例）`gemini === "N"` かつ（`digest` が短い | 禁止定型検出 | タイトルに個人情報っぽいパターン）など **複合条件**（`gemini=N` 単独では立てすぎない）。

---

## 4. 重大度による上限例外（ガードレール必須）

定数は **`AGENTS.md` に明記**（本リポジトリの憲法）。実装では **環境変数で上書き不可**にするか、`COLLECT_EXCEPTION_MAX_PER_DAY` のみ許可し **上限 3 を超えて解釈しない**などの防御を推奨。

| ルール | 案 |
|--------|-----|
| 通常枠 | 既存どおり `COLLECT_MAX_NEW_PER_RUN`（既定 3） |
| 例外枠 | **1 日あたり最大 3 件**（ランサム＋国内等の条件合致時のみ消費） |
| 条件 | タイトル＋抜粋に対するキーワード集合（ホワイトリスト）。**OR の羅列を増やしすぎない**（誤検知＝例外枠浪費） |
| カウンタ | 当日既に登録した件数を kintone **クエリ（作成日時＝今日）**で数える、または **内部アプリ 1 レコード**でカウンタ（実装選択） |

**無限追加防止**: 例外も **日次ハード上限（通常＋例外の合計上限）** を設けるとより安全（例: 合計 6 件/日 上限）。必要ならフェーズ2.5 で追記。

---

## 5. 実装順序（推奨）

1. kintone 631 にフィールド追加 → CSV / `field-codes.ts` 更新  
2. メタデータ保存のみ（例外ルールなし）  
3. `needs_review` ロジック  
4. 例外枠＋日次カウンタ＋合計ガード  
5. 手動テスト・本番は閑散時間帯に `collect` 1 回

---

## 6. テスト

- スタブ RSS またはコピー環境で **通常 3 件＋例外 3 件**が上限で止まること。  
- 同日再実行で **例外枠が二重に消費されない**こと。
